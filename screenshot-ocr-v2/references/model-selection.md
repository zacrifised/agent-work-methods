# 模型选型与成本账
## 口径（先统一，否则数字没有意义）
```
CER = 编辑距离(参考文本, OCR文本) / 参考文本长度
准确率 = 1 - CER
```
**标点、引号样式、全角半角全部计入。** 只算汉字会让数字好看 30% 以上，是自我欺骗。
## 首选配置
| 场景 | 模型 | 单张耗时 | 实测准确率 |
|---|---|---|---|
| **低容错 / 关键文本**（PRD、需求、合同、验收标准、测试用例、配置） | **PP-OCRv5 server** | ~56 s | **99.87%** |
| 高文本量 | 同上 | 同上 | 同上 |
| **批量** | 同上，单进程串行、不降配；提速走 GPU | — | 见下"批量" |
| 高容错 / 粗读 / 建索引（**不需要复核**的场合） | PP-OCRv4 mobile | ~6.4 s | 98.86% |
**唯一的分流依据不是"是否关键"，而是"这份结果会不会被人工复核"**
（低容错 ⇒ 必然复核 ⇒ server 反而更快）。
**PP-OCRv5 mobile 实测更差（95.75%，会整行漏掉），不要图快选它。**
## 依赖环境

Python 3.9+，依赖包：

| 包 | 用途 | 已知可用版本 |
|---|---|---|
| `rapidocr-onnxruntime` | 主 OCR 引擎 | 1.2.3 |
| `rapidocr` | 引擎 API 与模型枚举 | 3.10 |
| `jieba` | 中文分词（分歧裁决） | — |
| `pypinyin` | 拼音辅助 | — |
| `pillow` | 图像处理 | — |
| `opencv-python` | 图像分析 | — |
| `rapidfuzz` | 字符串相似度 | — |

**安装**：`pip install rapidocr-onnxruntime rapidocr jieba pypinyin pillow opencv-python rapidfuzz`
版本不符时优先按上表锁定；引擎 API 随版本变动，报 `must be Enum Type` 时先核枚举传参。
```python
from rapidocr import RapidOCR, OCRVersion, ModelType
eng = RapidOCR(params={"Det.ocr_version": OCRVersion.PPOCRV5, "Det.model_type": ModelType.SERVER,
                       "Rec.ocr_version": OCRVersion.PPOCRV5, "Rec.model_type": ModelType.SERVER})
out = eng(path)          # out.txts / out.scores / out.boxes
```
两个 API 坑（都实测踩过）：
- `ocr_version` / `model_type` **必须传枚举**，传字符串报 `must be Enum Type`。
- `out.boxes` 是 numpy 数组，`list(x or [])` 抛歧义错误，要写 `list(x) if x is not None else []`。
成本链条包含识别耗时与下游复核耗时两项，下表给出两模型对照。
### （一）低容错必然复核，复核成本随错误数线性增长
| | mobile | server |
|---|---|---|
| 识别 | 6.4 s | 56 s |
| 错误数（本例 1578 字） | 18 | 2 |
| 复核（每处对图比对约 15 s） | 18 × 15 = **270 s** | 2 × 15 = **30 s** |
| **端到端** | **≈ 276 s** | **≈ 86 s** |
**server 端到端反而快约 3 倍，残余错误还少 3 倍。**
### （二）错误往下游传播，代价不在 OCR 环节结算
粗 OCR 出错 → 语义变化 → **理解偏差** → 基于偏差做出的产物出错 → 返工。
同一段文字，OCR 换了几个字，下游的评分/结论随之改变；判据只建立在 OCR 读到的文本上。
PRD 上的同一个错，代价是一个测试周期或一次返工。
**OCR 环节的 1 处错，结算在下游，而且会放大。**
**盈亏平衡**（换 server 多花 49.6 s/张，换回少 16 处错、约 8 处改变语义）：
> 只要 **漏网率 × 单次语义错误的返工成本 > 6.2 秒**，server 就赢。
| 漏网率 | 单次返工成本 | server 的收益 |
|---|---|---|
| 20%（复核一般） | 1 小时 | **116×** |
| 5%（复核认真） | 30 分钟 | **14×** |
| 1%（复核极严） | 1 小时 | **5.8×** |
| 1% | 10 分钟 | ≈1×（刚好打平） |
要让 server 不划算，需要"漏网率 1% 且返工只要 10 分钟"同时成立。
**结论对假设极不敏感，不需要每次重新权衡。**
### （三）批量的墙钟时间 → 走 GPU，不要开多进程（实测反直觉）
真正的约束是**延迟**不是成本。但延迟的正解**不是**多开进程/子 agent——
本机（12C/20T + RTX 3080，CPU 路径）实测并发反而更慢：
| 配置 | wall clock | 吞吐 |
|---|---|---|
| 1 进程（默认线程） | 73.2 s | **0.82 张/分** |
| 2 进程（OMP=8） | 235.9 s | 0.51 张/分（**只有单进程的 0.62×**） |
| 4 进程（默认 20 线程） | 严重抖动，>14 min 未完成 | — |
原因：PP-OCRv5 server 单进程已把 20 个逻辑核吃满；一旦限制线程数，
单张从 71.5 s 恶化到 230.8 s（3.2×），而 N 个进程只换回 N× 名义并行，净亏。
**结论：CPU 路径下批量请单进程串行。**
批量提速唯一有效的办法是 **GPU**（`onnxruntime-gpu` + CUDA，本机 RTX 3080 可用）。
另外**不要给每个 worker 留默认线程数**，80 线程抢 20 核会直接抖动。
（多开子 agent 能并行的是**语义判读**这类 IO/推理任务，不是 OCR 本身。）
该方案有两处硬伤：
1. **时间不够。** 50 s 窗口要校对 1578 字 = 31.5 字/秒；
   对图逐处比对人的速度约 3–8 字/秒，差 4–10 倍。
2. **机制上要通读。** 语义校对需要一个懂语言的读者通读全文，
   1578 字通读 + 逐处取证远超 50 s。（注意：不能说"语义校对抓不到形近替换"——
   实测抓得到，见 `semantic-proofreading.md`。**时间**才是硬约束。）
粗 OCR 唯一合理的角色是**路由 / 分流**（这张图有没有文字、大概多少字、在哪个区域），
不要拿它当答案。
