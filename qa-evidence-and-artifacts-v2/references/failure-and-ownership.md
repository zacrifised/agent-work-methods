# 失败分类与上下游 ownership

## 按复现性分三条路（详解，SKILL.md 里是简版）

### 必现：沿 E2E 链定位，用方向不对称

**真源在方法论内核 P1**（正向只能排除、负向才能定位、只有 E2E 能宣布通，以及四种反例）。本文件不复制正文。

E2E 链上的具体用法（这部分是本 skill 特有的）：

- 从头到尾逐节点遍历，**靠负向信号定位断点**；只有 E2E 能宣布通 / 不通
- 两级推理不能并成一级：**节点异常 ≠ 阻塞用户**，中间隔着"是否关键路径"
- 只看状态码等于没测——要校验返回内容是不是用户要的东西
- 必须用与用户一致的场景：同样的登录态、同样的入口、同样的客户端

### 偶现 / 复现路径不明：先锁变量

把不确定的变量逐个锁死——环境、账号、时间窗、数据状态、并发、缓存状态、
身份角色、快慢路径时序。目标是把"看起来偶现"变成**可重复触发的路径**，
再进 `排查方法论 skill` 的主循环。

- **锁不死的变量要写进证据缺口，不能当不存在**
- 时间驱动的状态（定时流转、超时、冷却、TTL）先算三个时间点
  （见 `artifacts-and-cleanup.md`），别把"还没到临界点"判成缺陷
- "偶现"里有相当一部分是**本质必现但路径没锁死**——这是最值得投入的一类，
  也是最容易被登记成"偶现/暂不处理"而永久搁置的一类

### 第三方：只定位，不追根因

没有日志、没有代码、没有本地可控变量时，**不具备深入分析的条件**：

- 判到"是第三方"即止，输出**规避方案 + 上报 + 该依赖的假设**
- 不要编一个看起来专业的根因
- 把第三方当黑盒，验证的是"它对我们的契约"（超时、限流、降级、返回结构变化）

## 归类消解顺序

```
脚本误报 → 工具链 → 入口/配置 → 环境 → 鉴权 → 数据 → 第三方 → 产品实现
```

按**排除成本从低到高**排，不是按"像不像"排：

- `脚本误报` 最便宜——重跑一次、核一下期望值就能判掉
- `工具链 / 入口 / 配置 / 环境 / 鉴权` 中等——改个变量再试
- `产品实现` 最贵——一旦判下去就要占用开发资源，所以**必须最后落**

## 失败先分类（分类本身就是产出）

遇到失败，**先分类再动手**，不要边猜边修。九类见 SKILL.md 的表格，此处补使用纪律：

- **失败分类本身就是交付物**，要在报告里单独写出来
- **不要把一切失败都包装成"产品坏了"**——这在统计上会污染缺陷分布，
  让团队对真实质量问题失去敏感度
- 也不要反向滥用：把真实产品问题归为"环境问题"来降低优先级。
  **归类必须给出可复核依据，不是感觉**
- 认定为"证据缺口"类时，**不能按成功闭环汇报**

## 上下游 ownership 与 route back

context / case / assertion manifest / runner / 分层策略 / 执行报告，
**各自 owns 什么要分开**。

- **下游发现上游预期错了 → route back 给上游订正，不要在下游静默改口径。**
  例：执行时发现 case 期望与 PRD 不符 → 改 case 前先回问 PRD 归属方，
  并在变更记录里写明"原预期 / 新预期 / 依据 / 谁确认的"
- **静默改口径会切断追溯链**：下次同样的问题会再犯，且没人知道口径何时变过
- 每一层只对自己那一层的正确性负责，并对上游的错误**有上报义务**

> 这条是"缺 PRD / IDL 口径变化要触发下游更新"的前置：
> 没有 ownership 分界，回流就没有对象。见 `ticket-and-closure.md` §14.2。
