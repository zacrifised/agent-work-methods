# 提单、缺陷闭环与沉淀

## 提单要素

必须包含：前提条件、复现步骤、预期结果、实际结果、**发生概率**、**影响范围**、证据。

- 标题用**一句话人话**说清问题；复现步骤要让**不含作者的第三方能照做**，不依赖口头补充
- 发生概率：**用户未说明偶发时，默认写必现**，并在描述里注明这是默认值
- 影响范围要写清：影响端、是否兼容性问题、是否存在规避方式
- 证据材料优先来自结构化的证据包；**聊天里的判断只能作辅助上下文，不作主证据**
- **提单前查重**：用标题关键词 + 业务标识（房间号 / UID / 单号 / 版本 / 报错关键词）
  检索已有缺陷，避免重复单稀释统计口径
- 证据必须**对读者可触达**：上传成功 ≠ 能打开。成功标准是该缺陷的
  **详情页或评论区能回读到非空附件链接**，或描述里包含经过登录态验证的可点击链接。
  仅有内部 file token / stream URL 不算达标；不可达时降级为云盘或群文件链接，
  并回读分享权限、在描述里标明这是退化路径
- **不要声称某字段已自动填好**，除非现场写入并回读成功。
  字段能力不要只按**配置面**判断——配置面的形态（单选 / 必填 / 默认值）
  经常与真实 UI 或真实 API 行为不一致，以**现场写入并回读**为准
- 只有满足明确的静默通行条件才可绕过逐单确认；否则先展示草稿、字段取值与附件清单
- **关键证据缺失时写明缺口，不带猜测下结论**
- 无法确认 root cause 时，写清：已证实现象、已排除项、领先方向、候选机制、
  仍缺哪些证据、建议下一步查什么

## 自主提单的授权边界

若被授权直接建单（不经逐条确认），必须**同时**满足：

- **已确认为真问题**：按证据更新后极大概率确实是 bug，不是环境 / 数据 / 脚本误报
- **证据链基本完整**：现象、复现路径、关键日志或截图至少具备，缺口已显式标注
- **优先级达到约定阈值**（通常是最高两档）

不满足任一条 → 生成待确认草稿或证据包，**不建正式单**。
只有主观观感、缺少日志 / 截图 / 对照，或只是假设性风险时，一律不走自主提单。
责任端不能确定**不构成阻碍**（可由开发继续定位），但必须在单里写明"责任端待定"。

## 表达风格

- 面向 PM、QA、开发共同消费的结论，用**业务可读语言**写；
  技术术语必须服务于解释，不为显得专业
- 优先使用团队既有业务术语；自造术语要先定义
- 明确区分：**已证实问题 / 证据不足 / 需要决策 / 实现风险**

## 缺陷闭环与回流

复盘须把结论结构化收敛，不依赖翻评论和附件。

### 14.1 缺陷必须结构化收敛到最终结论

每条非平凡缺陷在关闭时，除了"已修复"，还要能回答：

- **最终结论**：真 bug / 需求变更 / 环境或数据问题 / 外部依赖 / 无法复现 / 重复单
- **责任端与根因层级**：哪一端、哪一层（契约 / 状态机 / 时序 / 配置 / 第三方）
- **右移原因**：未在更早阶段发现的环节（需求未覆盖 / case 缺失 / 断言太弱 /
  环境无法覆盖 / 自动化未接入 / 已知但被降级）
- **防复发动作**：补了什么 case / 断言 / 门禁 / 观测，还是明确选择不补（并写理由）

> **结论写在结构化字段里，不要只写在评论里。**
> 评论是过程，字段才是可统计、可复盘、可交接的资产。

### 14.2 PRD / IDL 口径变化要触发下游更新

- 口径变化（PRD、IDL、枚举、状态机、默认值）必须有**显式变更记录**：
  原口径 / 新口径 / 生效版本 / 谁确认的
- 变化必须**回流到下游资产**：受影响的 case、断言期望值、契约检查、巡检规则
- **没有回流的口径变化 = 下一次误判的来源。** 变更记录里要写明"已更新哪些资产"，
  不是"已通知相关同学"

### 14.3 case 更新点要可追溯到来源

case 的每次修改记录：变更动因（关联缺陷 ID / PRD 变更 / 重构）、改了什么、
改之前的期望是什么。让 case 的演化可解释，避免"期望值漂移后无人知晓"。

### 14.4 是否进入门禁要有决策记录

不是所有验证都该进 CI（选择标准见 `test-strategy-design`）。
**进或不进都要有记录**：进了，写明触发条件和失败后的处理约定；
不进，写明原因（成本 / 稳定性 / 依赖稀缺资源）和替代验证方式（何时手动跑、谁跑）。

### 14.5 机制化程度自检

- 换一个人接手，能否仅凭记录就知道"这条链路当前该怎么验、上次的判定依据"？
- 上季度的缺陷分布、右移原因、case 覆盖率变化，能否**不靠人工翻评论**就统计出来？
- 任何一个答案是否定的，说明那部分还停在个人能力，没变成团队机制

## 会话与规则沉淀

- **偏好一主题一会话**；同一主题可维持较长会话
- 历史上下文多于当前有效信息、主题多次切换、或执行明显变慢时 → **建议新会话**
- 建议新会话前，先给**可迁移摘要和下一步入口**
- **稳定、可复用、可解释**的用户纠正 → 沉淀到对应 skill 或 reference
- **一次性纠错不升级为通用规则**
- 修正规则属于专项流程时写到专项 skill；入口层只保留总则、边界和路由
