# 覆盖可反查、非 happy path 与变更影响面

## 覆盖要可反查，gap 不能静默通过

覆盖不是"模块扫过一遍"，而是**每一条需求点都能反查到验证结论**。

- PRD / 设计 / 原型里的**字段、状态、按钮、视觉标识、限制条件**，
  每一条都要能反查到四种归宿之一：
  `已覆盖 case` / `测试矩阵` / `out_of_scope（写明理由）` / `pending（写明阻塞原因）`
- **`gap` 不能静默通过。** 反查不到的项必须在报告里显式列出，
  不得因"没测到但也没出问题"而漏写
- 反查表的最小粒度应到**可验收的点**，不是到模块名。
  "登录模块已覆盖"不是覆盖，"第三方登录失败后的错误文案与重试入口已覆盖"才是

## 非 happy path 优先追问清单

评估需求、设计 case 或判断影响面时，**默认优先追问这些**（不是等出问题才想）：

| 类别 | 具体场景 |
|---|---|
| 边界与时序 | 边界值、临界时间点、并发与串行切换、快速连续操作、重复提交 |
| 弱网与中断 | 弱网、断网、超时、重试、断连重连、请求中断、页面刷新 / 回退 |
| 状态与多轮 | 多轮 / 跨轮状态残留、中途退出、取消、暂停恢复、旧数据迁移 |
| 降级与兜底 | 第三方失败、依赖不可用、降级路径、**兜底逻辑是否"被动推进"了状态** |
| 角色与权限 | 多角色差异、越权、并发修改同一对象、数据隔离 |
| 一致性 | 多端生产消费一致性、回显与持久化一致性、下游消费一致性 |

> 尤其警惕"靠兜底逻辑被动推进状态"：**最终状态是对的，但用户实际等待不可接受**，
> 而自动化断言会判通过。（分层落位见 `test-strategy-design`）
>
> 失败被兜底 / 降级 / 重试吞掉时，表面一切正常——验证要看实际行为与产出，
> 不看有没有抛异常。

## 变更影响面检查

评审新功能或重构时，必须检查对**旧功能和旁路功能**的影响，至少覆盖：

- 同模块旧链路
- 上下游服务
- **观测 / 日志**（改动是否破坏现有排查手段）
- 审核 / 风控
- 上传 / 缓存
- 跨端同步
- **自动化**（现有 case / E2E / 巡检是否失效）
- 运营 / PM 可见产物（报表、后台、通知）

> 本清单定「要查哪些面」的范围；判据与证据层按资源索引表中的路由指针查阅。
