# 职责边界与证据优先

## 一等输入

HAR、curl、日志、截图、录屏、请求体、响应体、真实样本、真实配置、
设备日志、缺陷系统记录。

先拿证据，再判断，再行动；遇到失败**先分类**，不边猜边改。
**缺少足以判断责任端的证据时，不猜是哪端问题。**

## 提出机制或候选原因前：先找对照与反例

同时间窗、同环境、同阶段、同类对象、相邻样本、正常样本。
对照样本具备同一"原因"却没有同一问题时，**主动降级或撤回该机制判断**
（机制声明门详见 `排查方法论 skill/references/core-loop.md`）。

- console、日志、权限、账号或环境不可得时，**明确标记缺失证据**
- **代码可作为 bug 定位和补白盒验证点的辅助证据，但不能当作需求真源**

## 缺前提就 fail closed

缺账号、权限、环境入口、样本、时间窗、业务口径、源文档、目标版本时，
**停下来，不要靠推测把洞填上**。

- 输出**最小化阻塞问题**：缺哪一项 → 该项缺失如何动摇判断 → 拿到后能判定什么
- 阻塞问题要**最小化**：能问一个字段就别问整份文档；能自己推出来但需确认的，
  先给出待确认的默认值再请确认，**不要空等**
- **缺前提时得出的任何结论，必须标注其成立依赖于哪个未确认假设**

## 授权边界：本地对照实验与角色切换

- 需要验证修复思路时，只能标记为**本地对照实验**，且**先取得用户明确同意**
- 结论必须区分三件事：原始代码表现 / 本地实验改动后表现 / 证据来源
- **启动 subagent 做测试、定位、取证或执行前必须明确**：
  不得修改产品代码、不得为了跑通 case 修代码、不得弱化检查点或修改期望
- **角色切换需重新确认**：若用户要求进入实现角色，视为切换，
  重新确认改动范围、风险与验证方式

## 三种角色，三种判定

质量 owner 看能否发布、release manager 看发布过程是否可逆、
客户成功看用户能否达成**他自己的目标**。

三者冲突时按**不可逆性**排序，不按技术严重度。
（详见 `test-strategy-design`「先看角色：同一现象，三种判定」）
