# QA 证据与产物纪律

## 范围

覆盖：确认问题、收敛责任边界、保留证据、输出复现 / 提单材料；以及输入上下文综合、
失败归类、覆盖反查、产物落盘与清理、源文档留存。
不覆盖：假设空间定位流程（→ 排查方法论 skill）；分层策略（→ 测试策略 skill）；
对外部用户的脱敏与通俗化（独立工序）。

## 完成判据

- 已有可追溯上下文包：源文档清单、范围映射、决策日志、数据/状态/边界上下文、开放问题
- 缺账号 / 权限 / 样本 / 期望口径时停下并列最小化阻塞项（fail closed）
- 证据足以判定责任端；不足时不猜是哪端
- 失败已按 8 类主类 + `证据缺口`（附加判定）归类并给可复核依据
- 覆盖可反查到每条需求点（字段、状态、按钮、限制条件），`gap` 不静默通过
- 产物写到工作区外，不污染业务仓库；清理与副作用写入结论
- 提单前查重，证据对读者可触达（上传成功 ≠ 能打开）
- 源文档按规范留存，文本与视觉证据交叉验证
- QA 不改业务代码；角色切换时重新确认范围、风险与验证方式

## WHEN → THEN

**WHEN**：测试 / 调查中需要确认问题、定责任端、留证据、写提单材料或审测试证据。
**THEN**：
1. 先按「QA 上下文综合」段把输入综合成可追溯包。
2. 判复现性（必现 / 偶现 / 路径不明），决定沿 E2E 链还是进排查主循环。
3. 判责任端主类（8 类互斥 + `证据缺口` 附加），按排除成本从低到高消解。
4. 产物落盘到工作区外；造数与清理路径记录；时间驱动状态做验证。
5. 写覆盖结论，逐条反查需求点；变更影响面与非 happy path 逐项过。
6. 提单前查重、核证据可触达；缺陷闭环与口径回流。
7. 结论区分【已证实 / 证据不足 / 需决策 / 实现风险】；证据不足不写成结论。

## QA 上下文综合

证据层先于 case / L1 / 执行 / 复盘。本 skill 只 owns：

- **source inventory**：源文档清单与等级
- **scope map**：需求 → 模块 → 消费端映射
- **decision log**：口径决策与来源
- **data / state / boundary context**：数据、状态、边界上下文
- **open questions**：未决问题

不 owns 正式 case 资产、断言 manifest、runner 实现、测试执行或产品预期定义。
源文档 / 视觉证据 / 文本提取 / 用户口径互相冲突 → 标待确认或 route back，不在本层静默定口径。
输入疑似缺文档时，仅在用户授权并指定范围内做低等级 source discovery，聊天记录不作为 SSOT。

## 职责边界

- 目标：确认问题、收敛责任边界、保留证据、输出复现信息或提单材料。
- 不直接改开发代码让测试通过；不把「本地修后通过」当「待上线代码没问题」。
- 不以闭合真正 root cause 为硬完成条件——显著降低他人继续定位成本即高质量产出。
- 启动子 agent 做测试 / 定位 / 取证前声明：不得改产品代码、不得为跑通修代码、
  不得弱化检查点或修改期望。
- 用户要求进入实现角色时视为切换，重新确认 governing skill、范围、风险与验证方式。
- 同一现象在质量 owner / release manager / 客户成功三种角色下判定不同，
  冲突时按**不可逆性**排序，不按技术严重度。

## 硬规则

1. **证据优先**：先证据后判断后行动；缺责任端证据不猜。
2. **缺前提 fail closed**：缺账号 / 权限 / 样本 / 口径 → 列最小化阻塞项。
3. **产物写到工作区外**（`.artifacts/` 或系统临时目录），不污染业务 repo。
4. **失败先分类**（8 类主类 + 证据缺口附加），分类本身是交付物。
5. **覆盖可反查**每条需求点，`gap` 不静默通过。
6. **清理与副作用是结论的一部分**，清理失败 = 独立 `cleanup_required` 类。
7. **提单前查重**，证据对读者可触达。

## 失败归类（主类互斥，证据缺口附加）

### 判复现性（第一步）

| 复现性 | 特征 | 走哪条路 |
| --- | --- | --- |
| 必现 | 同一路径稳定出现 | 沿 E2E 链定位断点 |
| 偶现 | 同路径时有时无 | 先收敛复现路径，再进排查主循环 |
| 路径不明 | 看似偶现，实为路径没锁死 | 最危险，常被误登记为「偶现」而放弃定位 |

### 8 类主类 + 证据缺口（附加判定）

| 类别 | 典型表现 |
| --- | --- |
| 入口 / 配置 | 环境、泳道、host、feature flag、版本不对 |
| 数据 | 造数不满足前置、脏数据、未落库、状态未收敛 |
| 鉴权 / 权限 | token 过期、scope 不足、租户隔离、登录态失效 |
| 工具链 | 脚本、runner、构建、依赖、版本漂移 |
| 环境 | 机器、网络、设备、时区、资源不足 |
| 产品实现 | 真实的功能 / 逻辑 / 契约缺陷 |
| 第三方服务 | 外部依赖超时、限流、降级、返回结构变化 |
| 脚本误报 | 断言写错、期望值过期、等待不足、读错 record |
| 证据缺口 | 结果可能对但无证据证明 → **不能按成功闭环汇报**（附加判定） |

主类用于「谁负责」，只写一个；root cause 层面允许多因。
归类必须给可复核依据，不把真实产品问题归「环境问题」降优先级。
第三方只定位不追根因：判到即止，输出规避方案 + 上报。

### 多类消解顺序（排除成本从低到高）

`脚本误报 → 工具链 → 入口/配置 → 环境 → 鉴权 → 数据 → 第三方 → 产品实现`

## 反例

- ❌ 无证据就定责任端；缺前提靠推测补洞。
- ❌ 产物写进业务仓库；清理失败不写进结论。
- ❌ 把一切包装成「产品坏了」；把产品问题归「环境问题」降优先级。
- ❌ 覆盖只到模块级；`gap` 静默通过。
- ❌ 源文档未留存、文本与视觉未交叉验证就下结论。
- ❌ 上传成功当证据可触达；不查重就提单。
- ❌ 结论不区分已证实 / 证据不足 / 需决策 / 实现风险。
