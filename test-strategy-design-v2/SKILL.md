# 测试策略设计

## 范围

覆盖：从项目特征推导质量目标、分层落位、CI/CD 接入边界、稀缺验证资源门禁、
模拟器与真机边界、L1 → 开发 E2E 回流。
不覆盖：单次问题定位、单个 case 编写、测试执行本身、产品放行结论。

## 完成判据

- 已识别项目特征（八个维度）与由此推导的测试痛点
- 质量目标已定义且带防滥用边界，不以「缺陷数最小化」为目标
- 分层方案写明每层的落位理由、自动化可行性与不覆盖风险
- CI/CD 接入写明哪些层级进、哪些不进及理由；高成本稀缺资源不进常规 CI
- L1 数据链三条判据满足（真实数据 fixture、runner/evidence 分离、routing gap 登记）
- 模拟器通过的结论标注不覆盖范围；依赖真机特性的 case 标 `manual-real-device` 或迁 L2
- 输出含风险、应落层级、断言方式、CI 位置、不覆盖风险、稀缺资源预算
- 自检项全部有答案；缺项明确标为「待补输入」

## WHEN → THEN

**WHEN**：要设计 / 调整 / 评审测试策略、分层方案、CI/CD 门禁或稀缺资源使用。
**THEN**：
1. 先判角色（质量 owner / release manager / 客户成功），同一现象三种判定。
2. 定质量目标（不是缺陷数最小化），过三条防滥用边界。
3. 识别项目特征八维，逐维推痛点与应对。
4. 选分层：L0 / L1 / L1P / L2 / L3，逐层写落位理由与不覆盖风险。
5. 定 CI/CD 边界：哪些层进、触发时机、哪些不进及理由。
6. 过 L1 数据链三条判据；从 L1 回流开发 E2E 前核迁移三条件。
7. 按输出模板成文，跑策略质量自检。

## 硬规则

1. **策略由项目特征推导**，不照搬分层模板；无通用最优解。
2. **质量目标不是缺陷数最小化**，且必须过三条防滥用边界。
3. **不牺牲质量门禁**；效率与成本是约束不是目标。
4. **高成本 / 依赖第三方的验证不进常规 CI**；CI 经常红等于门禁失效。
5. **模拟器通过 ≠ 真机通过**；依赖真机特性的 case 标 `manual-real-device` 或迁 L2。
6. **L1 断言从需求 / 设计 / 已确认口径来**，不从代码反推。
7. **L1 不替代人工体验判断**（性能、发热、电量、真实网络、权限、音频、实时链路）。
8. **fixture 必须是真实数据**，不用 mock / DB seed 冒充；routing gap 显式登记。
9. **三角色判定冲突时按不可逆性排序**，不按技术严重度。

## 核心主张

策略由项目特征决定，没有通用最优解。不要照搬分层模板。
`项目特征 → 测试痛点 → 应对策略 → 分层落位 → CI/CD 边界 → 优先级`

## 先看角色

同一现象在三种角色下判定不同；混淆角色是质量讨论最常见的吵架来源。
先确定本次站在哪个角色下决策。

| 角色 | 核心问题 | 关注什么 | 判「问题」的标准 | 失败代价 |
| --- | --- | --- | --- | --- |
| 质量 owner | 这个版本能不能发？ | 缺陷分布、右移率、覆盖可反查、门禁有效性 | 违反**已确认的业务 invariant** | 漏测导致事故 |
| Release manager | 发的过程可不可控？ | 版本可追溯、回退路径、发布前置就绪、变更影响面 | 是否存在**不可逆 / 不可回退**步骤 | 发版失败且无法快速恢复 |
| 客户成功 | 用户能达成自己的目标吗？ | 端到端真实场景、可达性、体验、文档培训 | 是否阻碍用户完成**他自己的目标**，而非产品定义的成功 | 用户放弃、投诉、流失 |

**仲裁原则**：三者冲突时按**不可逆性**排序，不按技术严重度。
例：不影响主流程的展示错位，质量 owner 判 P2、release manager 认为不阻塞；
但若出现在对外交付场景，客户成功视角下可能是 P1——用户目标不是「用没 bug 的产品」，
是「顺利办成他那件事」。发布前多问一句：最坏时刻出现在用户面前，他还办不办得成。

## 先定目标

质量目标不是「缺陷数最小化」：把优化对象从缺陷数量换成**缺陷后果分布**。
三条防滥用边界（缺一即退化为「放水许可证」）：

1. 目标必须绑定业务阶段与用户可感知结果，不是内部指标。
2. 降级 / 不测的决定必须写明不覆盖风险与消费方。
3. 低优先级不等于不记录；缺口要可反查。

## 第一步：识别项目特征（八维）

逐维问「当前项目是什么样」，再看它带来什么测试痛点：

1. 代码是否大量由 AI 生成、人看不懂实现
2. 是否倒排期、边测边改
3. 需求是否易漏（含 AI 读需求漏项）
4. 体验项是否难以自动断言
5. 人工是否能低成本兜住某些自动化项
6. 是否有稀缺昂贵验证资源（真机 / 第三方 / 推理预算）
7. 是否无灰度、发布不可逆（直播 / 线下活动 / 硬件 / 车载）
8. 是否有不可消除的架构性约束（第三方 SDK / 选型代价）或现场环境与实验室不等价

## 第二步：按特征选应对策略

每类特征对应一组应对，写完策略后逐条回看是否漏配：

- **AI 生成代码 / 倒排期**：QA 中间层保零信任断言，先保证关键主链路与风险。
- **需求易漏**：输入包强约束，显式覆盖索引逐条反查，缺项 fail closed。
- **体验项难断言**：明确标人工 / 真机，不硬塞进自动化。
- **人工能低成本兜住**：不必自动化，把成本留给稀缺项。
- **稀缺昂贵资源**：专用账号、masked 变量、资源锁、低峰时段、样本量预算。
- **无灰度 / 不可逆发布**：发布前人工门禁，不把高成本流程塞进常规 CI。
- **架构性约束 / 现场不等价**：只定位不追根因，输出规避方案 + 上报。
- **硬件约束反向决定范围**：先列硬件能支撑的验证边界，再定 case 范围。
- **开发侧 E2E 与真实体验脱节**：QA 保留 L1 零信任断言，不依赖开发侧通过率。

## 第三步：分层框架

| 层 | 定位 | 要点 |
| --- | --- | --- |
| L0 | 开发自测 | 开发 own，QA 不替它兜底 |
| L1 | QA 中间层 | 机器可断言、零信任主断言、真实数据流 |
| L1P | 线上无感巡检 | 专用账号、masked/protected 变量、resource_group 防并发、低峰时段、失败通知、artifacts 留档 |
| L2 | 真机 / 人工体验门禁 | 稀缺资源，发布前人工执行 |
| L3 | 更高成本现场验证 | 按项目特征决定是否设立 |

- **L1 应覆盖**：主链路、状态机、跨端消费、数据持久化与回显、可机器断言的边界。
- **L1 不应替代人工判断**：性能、发热、电量、真实网络、权限细节、音频、实时体验。

## 第四步：CI/CD 接入边界

关键决策不是「能不能接」，而是「哪些层级应接入」：

1. **每次 MR / commit**：lint、单测、契约、case 资产一致性、最小低成本 E2E。
2. **合并联调分支 / 手动触发**：环境部署验证、后端 E2E、L1 状态机断言。
3. **线上定时**：L1P 无感巡检（见上）。
4. **打稳定 tag**：记录包版本、依赖指针、环境、配置快照、分发状态。
5. **发布前**：人工执行 L2，**不把高成本稀缺资源流程放进常规 CI**。

高成本、耗时、依赖第三方的验证不进常规 CI——CI 经常红，团队会习惯忽略红灯，门禁失效。

两条坑：
- 不默认把仓库 `build` 当完整前置门禁，除非验证过 clean checkout 能生成所有被产品导入的契约 /
  生成客户端包；本机 `dist`、缓存、作者本地生成物不能当 CI readiness 证据。
- 模拟器通过 ≠ 真机通过；结论写明不覆盖范围，真机依赖的 case 标 `manual-real-device` 或迁 L2。

## 第五步：从 L1 回流开发 E2E

QA 先在 L1 保留零信任断言；某断言稳定、低成本、机器可重复、与实现无强耦合时，
再推动开发纳入 L0 / 开发 E2E。迁移前确认：

1. 断言源是需求 / 设计 / 已确认口径，不是代码反推。
2. 失败信息能定位到用户链路或契约，不是脆弱实现细节。
3. 迁移后 QA 仍保留必要抽样或准入检查，不因开发接入删除关键门禁。

## L1 数据链与证据契约

1. **真实数据 fixture**：只能指真实前置流程生成或锁定的 real-data fixture；
   不能指 mock 数据、DB seed、本地 JSON 或 request override——否则 L1 证明的是脚本自己造的世界。
2. **runner plan 与 evidence contract 分离**：谁在哪个环境跑、产物如何寻址是一回事；
   主断言来自用户可感知结果、诊断断言只作解释是另一回事，分别定义不混写。
3. **routing gap 显式登记**：case / 断言无法落到当前 runner 的部分，标缺口与消费方，
   不静默降级为「已覆盖」。

## 默认优先级

1. 不牺牲质量门禁。
2. 先保证关键主链路、关键风险、关键体验。
3. 优先降低稀缺资源成本。
4. 优先提高可复用性与长期 ROI。
5. 最后才追求执行速度与 token 使用效率。

效率与成本是约束不是目标——**先把门禁做对，再做快**。

## 输出模板

- 当前风险或问题类型
- **应落层级**：L0 / L1 / L1P / L2 / L3
- **自动化可行性**：稳定自动 / 半自动 / 人工
- **断言方式**：UI / API / DB / 日志 / timeline / 录屏 / 人工观感
- **CI/CD 接入位置**（或不进 CI 的理由）
- **不覆盖的风险**（真机、体验、性能、第三方）
- 是否应推动开发 E2E 复用
- 稀缺资源预算与样本量

## 策略质量自检

方案写完问「这些信息我有没有」，缺任何一项都会明显降低质量：

- 开发侧现有 E2E 覆盖哪些链路、用什么断言、产出什么执行证据
- 现成 mock 能力有哪些、哪些第三方已有稳定替身
- 缺陷系统的状态流转、字段结构、评论习惯
- 真实可用的设备池、网络环境、多人协同资源
- 当前提测 / 发版 gate 的**真实**执行口径（不是文档口径）
- 各第三方服务的所有权边界、故障兜底策略、成本上限

## 反例

- ❌ 照搬分层模板，不从项目特征推导。
- ❌ 把质量目标定为缺陷数最小化。
- ❌ 高成本 / 依赖第三方的验证进常规 CI。
- ❌ 用 build 成功或模拟器通过当 CI readiness / 真机结论。
- ❌ L1 试图替代人工体验判断，或断言从代码反推。
- ❌ fixture 用 mock / DB seed 冒充真实数据流。
- ❌ 缺口静默降级为「已覆盖」，不登记 routing gap。
- ❌ 为追求速度先牺牲门禁。
