# 测试用例改写 Playbook

本 playbook 给出可重复执行的最小改写流程。

## 1. 先判定能不能开始

### 新需求 / 功能变更

必须具备：
- PRD
- 技术评审文档

否则：
- 不进入正式编写
- 只输出缺失项、当前可确认项、假设项、最小澄清问题

### bug 补洞 / 回归补点

可以不强制要求 PRD 和技术评审，但必须至少具备一类输入：
- bug 单 / 缺陷描述
- 复盘记录
- 用户为何将其定义为 bug 的说明
- 相关代码提交记录
- 修改点说明
- 用户澄清

否则同样不能进入正式编写。

## 2. 再判定输入该怎么用

统一按 4 级证据使用：
- S1：需求真源
- S2：设计与对齐材料
- S3：讨论与补充材料
- S4：实现与现状材料

固定规则：
- 预期结果只能由 S1 / S2 决定
- S3 只能补充意图、确认细节、发现最新决策
- S4 不能反推产品预期

### 2.1 非 bug 场景的参考顺序

如果在非 bug 场景下同时拿到了多类非规范输入，默认按以下顺序使用：
1. PRD
2. 原型 HTML（如有）
3. PRD 评审会议纪要（如有）
4. 技术评审
5. 技术评审会议纪要（如有）

规则：
- 缺哪层就跳过哪层
- 同层冲突不自行拍板，回到用户澄清

### 2.2 bug 场景的参考说明

- bug 补洞通常不强行套同样的优先级链
- 原因是 bug 材料常常更有限、更碎片化
- 应优先围绕“为什么这是 bug”去组织输入，而不是强拼完整文档栈

### 2.3 图示与富文本怎么处理

如果输入包含 PDF、docx、PPT、图片、截图、原型、效果图、流程图、时机表、表格、批注、删除线或颜色状态，先完成源文档处理，再写 case。

固定顺序：
1. 保留原件和 source inventory。
2. 提取可检索文本、表格、批注 / 修订和可见文字。
3. 渲染关键页或全部页面，做视觉复核。
4. 写 manifest，记录提取方法、视觉检查方法和失败项。
5. 把图示事实映射到风险 / 边界、测试点、case / matrix 或不覆盖项。

图示事实映射表：

| 图示位置 | 识别事实 | 风险 / 边界 | 测试点 | case / matrix / 不覆盖项 |
| --- | --- | --- | --- | --- |

文本提取和视觉复核冲突时，不自行裁决；先把冲突写进待确认问题。

## 3. 会议纪要 / 原声怎么处理

- 默认当作 AI 转写文本处理，不逐字机械采信
- 结合上下文读，不单独拿一句话下结论
- 默认主语言为中文，英文缩写与中文混用正常
- 除常见技术术语外，也可能夹杂少量短英文短语，例如 `trade-off`、`kick-off`
- “持续一个人发言”的文本现象，不代表观点只来自一个人

如果纪要 / 原声和 PRD / 用户澄清冲突：
- 先看用户澄清
- 再看 PRD 最新口径
- 再看已确认评论或方案结论

## 4. 协作文档平台评论怎么处理

- 评论不默认是噪音
- 评论可能直接改变 case 预期

处理顺序：
1. 先判断评论是否只是讨论
2. 如果评论明确完成方案确认、范围调整、规则澄清或例外说明，再判断其时间是否晚于正文最新修改时间
3. 若晚于正文，且语义明确改变口径，则按评论口径
4. 如果拿不到可靠时间，不猜，先向用户确认

## 5. 什么时候可以看代码

### 新需求 / 新功能

- 不看待编写对象自身代码
- 不以待编写对象自身代码决定 case
- 不从待编写对象自身代码反推产品需求
- 如果用户明确指出“本需求类似某旧项目 / 旧仓库 / 旧玩法 / 旧后台”，可以把该相似对象的现有 case、文档或代码作为弱参考
- 弱参考只用于发现继承流程、历史风险、边界点和命名结构；不能替代当前需求真源或已确认澄清

### bug 补洞 / 已实现功能回归

允许看代码，但用途只限于：
- 理解 bug 根因
- 补白盒验证点
- 识别边界与异常

禁止把“当前代码就是这样”当成“预期就该这样”。如果用户没有显式指定相似旧项目或旧仓库，也禁止自行找旧实现来套用新需求。

## 6. 正式写前的固定动作

### 6.0 判断是否是轻量分析

如果用户只要求测试点分析、测试场景设计或草案用例矩阵，可以先走轻量模式：
- 不要求新开分支 / worktree
- 不要求同步 YAML、coverage-matrix、mr-ready-note 或版本号；覆盖索引自校验用
  `check_assets.py --dir <资产目录> --light`，不强制 YAML 派生一致
- 仍要遵守输入 gate、证据等级、必要澄清和弱白盒边界
- 输出应至少包含：需求理解、待确认问题、方法选择说明、测试点清单、草案用例矩阵或覆盖映射

一旦用户要求落正式 case 资产，必须切回正式改写流程。

### 6.1 先抛澄清问题

至少检查：
- 需求边界是否明确
- 多角色职责是否明确
- 多端差异是否明确
- 异常流是否属于需求范围
- 回退 / 兜底策略是否明确
- 正文与评论冲突时的最终口径是否明确
- bug 是否已经被定义为缺陷而非预期行为

只要还有高影响歧义，就不能直接产出正式 case。

### 6.2 再决定是否先交付流程梳理

必须先给流程梳理的典型场景：
- MAJOR
- MINOR 且影响现有流程
- 多模块
- 多端
- 多角色协作
- 状态机 / 阶段切换
- 高风险、易产生理解偏差

流程梳理不要求一定是大图，也可以是局部流程图、时序图或结构化流程列表。

### 6.3 正式编写必须单开分支或 worktree

- 正式编写 case 时，不在当前分支直接落笔
- 默认应新开分支，或新开独立 worktree
- 如果当前分支已脏，优先 stash 现有改动，再进入本次 case 编写分支
- 提交时只提交本次 case 编写改动的文件，不带其他文件

## 7. 正式改写时的默认顺序

优先级固定为：
1. 先列测试点清单
2. 再判断现有 case 是否只需要补验证点
3. 再改旧 case
4. 最后才新增 case

资产同步顺序固定为：
1. 先改 Markdown 真源
2. 再同步 YAML
3. 再更新 coverage-matrix
4. 再更新 mr-ready-note
5. 执行生成后自检门禁
6. 如涉及结构变更，再更新版本号和评审物料
7. 如包含 review-atlas 或其他评审图，生成 `review-atlas.docx`，把正式 PNG 作为文档图片对象嵌入；保留 SVG 源图和正式 PNG，并实际看图验收。禁止生成 `review-atlas.md`，也禁止在 Markdown 中用 base64 内嵌图片。

`生成后自检门禁` 门禁：
- 无活跃 finding：记录无关注项，继续后续流程。
- 有活跃 finding：先向用户抛出标题、严重级别、影响和 fix 方向，等待裁决或按用户已给裁决修改。
- 修改后重跑结构校验；必要时再次调用 `生成后自检门禁` 确认 finding 是否收敛。
- 该门禁只用于 case 资产自检和决策面收敛，不把本 skill 扩展成自动化脚本或产品代码修改。

## 8. 每次都要主动检查的遗漏点

### 8.0 测试设计方法选择

复杂需求、草案矩阵或需要解释覆盖依据时，先按需求特征选择方法，再展开 case。按需读取 `method-selection.md`。

默认映射：
- 有输入范围、长度、格式、上下限：等价类划分 + 边界值分析。
- 有条件组合、开关、身份差异：判定表。
- 有状态变化、生命周期、流程节点：状态迁移。
- 有端到端业务流程：场景法。
- 有大量参数组合且全排列成本过高：正交试验 + 风险补点。

输出时应能说明：
- 选择了哪些方法。
- 每类方法覆盖了哪些测试点。
- 哪些高风险点不能只靠方法组合覆盖，需要单独补 case。

### 8.0.1 PRD 显式功能覆盖自校验

如果 PRD、设计稿、原型或评审材料已经明确写出某个编号小节、表格行、字段、控件、状态、文案、交互、角标、状态色或限制条件，case 资产里必须能查到覆盖它的证据。

补洞时先做一张轻量覆盖索引（字段与 `assets/coverage-index-template.md` 一致）：
- 来源锚点
- 需求事实
- 覆盖目标
- 覆盖证据（case ID / 矩阵行）
- 状态：`covered / out_of_scope / pending_clarification / gap`

修复动作另记在报告说明段，不占状态字段。

`gap` 不能静默通过。模块级覆盖完成后，还要回看 PRD 原文、表格和视觉证据做细节回填；富文本表格和原型交互里出现但文本提取没抽出的内容，也要按视觉事实处理。

### 8.1 传统黑盒数据设计

凡 PRD 或澄清给出长度、数量、金额、时间、枚举、人数、轮次、次数、图片比例、文件大小等约束，必须给具体数据，而不是只写“合法/非法”：
- 等价类：有效、无效、空值/默认值、格式错误、权限错误。
- 边界值：`min`、`min+1`、典型值、`max-1`、`max`、`max+1`；允许空时单独列空。
- 状态转移：合法跳转、非法跳转、重复跳转、回退/恢复、终态后继续操作。
- 错误推断：前导零、空格、超长中文/英文/emoji、特殊字符、重复点击、网络重试、历史残留、缓存命中、权限错配。

例：主播名称允许空且最多 50 字时，至少覆盖空、1、49、50、51 字；如果前端限制无法输入 51 字，还要补“前端阻止输入 51 字”和“后端/接口拒绝 51 字”两个观察点。

### 8.2 正反向边界与断言精度

对模式分流、入口分支、状态分支、配置开关、权限分支、合法/非法输入等场景，必须写清：
- 什么条件进入 A。
- 什么条件不得进入 A。
- 什么条件进入 B。
- 什么条件不得进入 B。
- 非法、缺失、冲突输入进入什么错误态，且不应产生哪些持久化或下游副作用。

对跨文件或跨视图覆盖关系，必须做双向校验：
- `case.e2e_refs` 是否和 `e2e-cases.cases` 互相包含。
- `coverage-matrix` 是否由同一套映射生成或人工核对。
- `mr-ready-note` 是否没有低报仍待决策的 finding。

对累计值、金额、计数、榜单、导出对账等数据一致性断言，必须写清：
- 统计范围和时间窗。
- 去重键或事件唯一标识。
- 单位和标准化口径。
- 退款、撤回、异常、重复事件是否计入。
- 用什么原始数据或接口结果复算。

如果上述 schema 或聚合口径未确认，不写成“必须一致”的强断言；应写成待确认项、联调前置或探索性记录项。

### 8.3 常识性 bad case

即使 PRD 没明确写，也要判断是否需要覆盖：
- 回音
- 明显延迟
- 卡死
- 无法恢复
- 多端同步严重错位
- 核心交互体验不可接受

### 8.4 异常流

每个关键主流程至少检查是否需要纳入：
- 输入异常
- 状态切换异常
- 权限 / 角色异常
- 网络 / 重试 / 恢复异常

### 8.5 历史 bug 反推缺口

对 bug 驱动的补充，必须回答：
- 原 case 为什么没挡住
- 本次补的是验证点、边界还是新增 case
- 补完后回归集是否需要扩容
- 缺口来源属于：PRD 未写、PRD 更新未同步、澄清缺失、case 断言不够细、风险边界未推导、跨端联动遗漏、执行未覆盖。

### 8.6 变更后一致性

凡涉及新增、编辑、删除、上下架、状态流转、补填、配额/计数/预约人数变化，必须追问：
- 操作前是什么值？
- 提交了什么值？
- 请求和响应关键字段是否正确？
- 详情/列表/数据库或服务端查询是否更新？
- 刷新或重新进入后是否仍回显最新值？
- 下游客户端、H5、后台其他页面或媒体网关是否读到同一个值？
- 重复操作或反向操作是否被去重/阻断/正确收敛？

### 8.7 多轮/状态机重置

凡涉及多轮游戏、多阶段流程或状态机，必须检查：
- 阶段进入时只展示当前阶段元素。
- 阶段停留时部分角色已提交、长等待、超时和重试不会误推进。
- 阶段退出时弹窗、loading、toast、OS、字幕、音频、视频流、图层、临时输入和缓存被清理。
- 下一阶段不会串上一阶段图层、音频、字幕、输入、图片、参考图或 CTA。
- 下一轮会清空上一轮输入、选择、命中、分数、徽章、Ready、倒计时等状态。
- 终局不会继续出现前序阶段 CTA 或进入下一轮。

如果 PRD 明确写“复用某旧版本流程 + 新增/改造若干步骤”，必须额外检查旧版本行为是否被错误带入。尤其是 OS、字幕、音频、阶段 CTA、图层、徽章、效果标签、图片来源和 native/iOS 切换时机，不能只因为底层实现复用就默认沿用旧版本。

如果相似旧项目 / 旧仓库只是用户提供的参考，不是当前需求真源：
- 先列“参考对象可借鉴点”和“当前需求必须重新确认点”
- case 预期仍回到当前 PRD、技术评审、设计稿或用户澄清
- 参考对象里的历史缺陷和边界样本可转成风险检查点，但优先级不能直接照搬

PRD 的效果图和阶段图也应转成断言：某效果只出现在最终阶段图里，且阶段流程描述也指向最终阶段时，应补“前置阶段不展示该效果、最终阶段展示该效果”的正反向验证。

### 8.8 跨端/跨模块消费

凡一个模块生产数据、配置、状态、链接、图片、视频或文本，另一个模块消费，必须补交叉验证：
- 管理后台配置 -> H5/客户端展示。
- 管理后台补填/上下架 -> 公众号节目单、纪念品、回放入口。
- 服务端状态 -> 管理后台列表/详情/客户端阶段。
- 图片/视频资源 -> 预览、下载、保存、鉴权。
- FE 展示时机 -> iOS/WebView/native bridge/RTC/视觉参考图。

### 8.9 视觉压力样本与异步残留

视觉类 case 不能只写“不遮挡、不拉伸”。至少给 1-3 个样本：长文案、短中文名、英文长词、emoji、边界数字、方图/竖图/横图、多个徽章/标签/Ready/字幕叠加、小屏/大屏。

涉及音频、字幕、OS、视频流、WebSocket、RTC、动画、loading、toast、弹窗、轮询、缓存或重连时，必须检查切阶段、刷新、重进、取消和完成后的残留。

### 8.10 交互命中、环境开关与对象绑定

从历史 bug 回补 case 时，还要额外检查以下三类容易漏掉的验证点：

- 交互命中：链接/按钮/滑杆/拖拽贴纸是否只在目标区域生效；非目标区域、相邻控件、屏幕边缘和禁用态是否不会误触。
- 环境与数据源：feature flag、灰度、联调开关、mock、默认值、缓存、首屏冷启动和日期滚动是否被写成前置或断言；不要用静态样本证明动态数据逻辑。
- 对象绑定：多人场景里用户、座次、房主权限、媒体流、配额、聊天/静音和请求生命周期是否始终绑定到正确对象；换位、踢人、退出、取消、重连、切游戏后都要按风险复查。

### 8.11 公开 H5 / 公众号兼容性矩阵

面向全量用户发布的公众号 H5、公开 Web 或 App WebView，必须检查是否已有具体兼容性矩阵：

- 不能只写“iPhone 兼容”或“Android 兼容”，必须列设备型号、系统版本、微信/容器版本。
- 至少覆盖官方最低支持系统、当前主流系统、当前最新系统。
- 至少覆盖 iOS 小屏/大屏、iPadOS、Android 主流品牌、HarmonyOS、折叠屏/平板、桌面微信。
- 必须包含字体/显示缩放、横竖屏或折叠态、弱网刷新/重进、返回链路。
- 公众号全量发布前应有 P0 发布门禁 case，并输出矩阵执行表。

## 9. 输出质量要求

- 标题用用户可观察结果表达，不写成作者脑内状态
- 步骤与预期一一对应
- 正式 case 前应能看到测试点清单或覆盖映射，避免一上来直接铺表格
- 每条 case 应写出具体测试数据和主要设计方法；不适用时说明原因
- P0 / P1 case 应能解释业务价值，至少追溯到放行风险、核心链路、历史缺口、用户损害或关键业务规则之一
- 多角色、多端、多阶段要显式写观察主体
- 技术验证点尽量写成明确值或明确判断方式
- 假设项单列
- 不覆盖项单列
- case 对 PM、开发、QA、agent 都要可读

## 10. 结束前的自检

至少确认以下问题：
- 是否仍存在未澄清的高影响歧义
- 预期是否全部可追溯到 S1 / S2
- 是否误把 S4 当成需求真源
- 是否遗漏 coverage-matrix / mr-ready-note / 版本号
- 是否已调用 生成后自检门禁；若存在活跃 finding，是否已抛给用户决策并记录状态
- 是否明确了假设项与不覆盖项
- 是否在 bug 补洞场景里写清楚了缺口来源


完成判据的真源是 `SKILL.md`「完成判据」节；正式资产用 `check_assets.py --dir <资产目录>`，轻量模式用 `--dir <资产目录> --light`，按 `EVIDENCE_JSON.observations` 由独立执行方复算，`ok` / 退出码只作辅助。
## 11. 最小验证场景

这个 skill 后续至少应能稳定处理以下场景：
1. 只有 PRD，没有会议纪要、原型、评论
2. 有 PRD 和评论，评论晚于正文并明确改口
3. 纯 bug 补洞，无 PRD / 技术评审
4. MAJOR 级需求
5. MINOR 级且不改流程
6. 新需求但只给代码和日志
