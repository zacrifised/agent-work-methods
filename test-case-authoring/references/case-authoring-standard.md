# 测试用例编写规范（跨产品通用）

## 1. 目的

本规范适用于所有产品的 case 产出，不绑定单一玩法或项目。

本规范覆盖 6 件事：
1. 真源与派生产物的关系
2. 写 case 前的输入与前置 gate
3. 单条 case 与 E2E 的写法
4. 优先级与执行分层
5. 版本管理方式
6. 对下游断言路由与自动化扩展的衔接方式

本文中的具体产品名、端类型、业务动作和样本值都是说明规则的例子，不是规则的适用范围。写任何新模块时，先抽象出当前需求真正涉及的通用测试对象：边界、集合、状态、归属、变更、消费链路、数据规模、异常恢复，再把示例替换为当前产品的真实对象。

## 2. 适用范围与角色定位

这份规范默认服务于：
- QA 编写或改写测试用例资产
- 需求变更、功能新增、体验优化、bug 补洞后的 case 维护
- 后续由 agent 参与的 case 生成、改写与结构化同步

这份规范不直接定义：
- 测试用例评审流程
- 用例执行流程
- 自动生成脚本实现
- 开发 E2E / TDD / BDD / QA L1 的可执行断言拆解和 runner 路由

默认角色定位：
- 编写 case 时，代入资深测试工程师角色
- 从客户可感知的黑盒场景、业务风险和验收结果出发
- 对代码实现保持零信任
- 对需求细节完整性也保持零信任
- 原输入有任何不明确时，只能澄清或标记待确认，不能擅自更改、补写或替产品定口径
- 通过澄清和结构化梳理来消除偏差，而不是通过猜测补齐

## 3. 真源治理

### 3.1 单一真源

- `Markdown` 是唯一人工编辑真源
- `YAML` 是派生产物，供机器执行、校验、统计和后续自动化使用
- 发生冲突时，以 `Markdown` 为准

### 3.2 执行规则

- 不直接在 `YAML` 上做需求级修改
- 若因紧急原因修改了 `YAML`，必须同次提交回写 `Markdown`
- 后续应补 `md -> yaml` 生成脚本，彻底消除手工双改
- 正式编写 case 时，必须单开分支或独立 worktree，不能直接在当前分支上执行
- 若当前分支已有脏状态，应优先 stash，或直接在独立 worktree 中完成本次 case 编写
- 若在独立分支、独立 worktree 或临时目录中完成 case 编写，结束后必须同步回写本地正式目录中的对应文件，避免本地查看内容与待提交内容漂移
- 提交时只允许提交本次 case 编写涉及的文件，不得混入其他无关改动
- 正式生成一版 case 资产后，必须立即执行生成后自检门禁。没有活跃 finding 才能继续后续流程；存在活跃 finding 时，必须先汇总给用户决策，不能静默继续。
- `review-atlas` 是图文评审交付件，不再生成 `.md`。默认生成 `review-atlas.docx`，图片必须作为文档图片对象嵌入；同时保留 `review-atlas-assets/` 下的可编辑 `SVG`、正式导出 `PNG` 和必要的生成脚本或数据。
- 禁止在 Markdown 中使用 `data:image/...;base64` 内嵌图片。Markdown 只适合作为可读真源、轻量索引或引用外置图片的本地说明，不作为需要图片自包含的协作文档平台上传件。
- 若生成 `review-atlas` 或其他评审图，默认先产出可编辑 `SVG`，再使用可用的 Python 图形库正式导出 `PNG`；优先使用 `cairosvg` 等稳定 rasterizer，禁止用 `qlmanage -t` 一类缩略图链路替代正式出图。
- 图导出后不能只检查“文件已生成”；必须至少做一次视觉验收，确认中文字体正常、边界未裁切、长文案未超出安全区，并确认 `review-atlas.docx` 中嵌入的是正式 `PNG`，不是 SVG 预览图或 base64 文本。

## 4. 输入与前置检查

开始正式写 case 前，必须先完成输入与前置检查。  
如果关键输入缺失，不进入正式编写，只能输出：
- 缺失项
- 当前可确认项
- 假设项
- 需要用户补齐的最小问题

### 4.1 先识别当前任务类型

必须先判断本次工作属于哪一类：
- 新产品从 0 建整套 case
- 已有套件增补
- 已有套件重构
- bug / 事故 / 复盘补洞

还要同步判断影响粒度：
- 单条 case 修订
- 多条 case 增补
- E2E 补链路
- 回归分层调整
- 整套版本升级

### 4.2 输入包强约束

#### 新需求 / 功能变更场景的必需输入

- `PRD`
- `技术评审文档`

没有这两项，不进入正式编写。
如果新需求只提供了代码、日志、HAR、console 或接口现状，也不进入正式编写；这些材料只能帮助理解现状，不能替代需求输入。

#### 强推荐输入

- 会议纪要
- 原声转写
- 原型
- 项目背景说明
- 用户自己的澄清
- 用户自己梳理的业务链路

#### bug 补洞场景的例外输入

bug 补洞不强制要求 `PRD + 技术评审`，但必须具备至少一类能说明“为什么这是 bug”的输入，例如：
- bug 单 / 缺陷描述
- 复盘记录
- 用户为何将其定义为 bug 的说明
- 相关代码提交记录
- 修改点说明
- 用户澄清

### 4.3 输入优先级与证据等级

为避免拿错材料定义预期，统一按 4 级输入使用。

#### `S1 需求真源`

- PRD
- 用户明确澄清
- 已确认的方案变更结论

#### `S2 设计与对齐材料`

- 技术评审文档
- 原型
- 项目背景说明
- 用户自梳理链路

#### `S3 讨论与补充材料`

- 会议纪要
- 原声转写
- 协作文档平台评论
- 授权群聊中的明确澄清、结论消息和文档发现线索

#### `S4 实现与现状材料`

- 代码
- 日志
- HAR
- console
- 接口现状
- 现有 case

#### 使用规则

- `预期结果` 只能由 `S1 / S2` 决定
- `S3` 用于补充意图、确认细节、发现最新决策
- `S4` 不能决定需求预期，只能用于：
  - bug 补洞
  - 补验证点
  - 白盒测试执行参考
  - 风险识别
- 若 case 后续会被 E2E、L1 或 CI 自动化消费，`S4` 仍不能成为通过条件。源码、变量名、handler、分支或组件存在性只能作为诊断线索；正式断言必须落到用户可观察行为、产品消费的数据、官方读回、日志/timeline 或明确的人工证据。
- 新需求 / 新功能的强约束是：不得依赖待编写对象自身代码。这里的“自身”包括目标玩法、目标后台、目标页面、目标服务、目标仓库或目标模块的当前实现。
- 若用户明确说明“本需求类似某个旧项目 / 旧仓库 / 旧玩法 / 旧后台”，该相似对象的现有 case、文档或代码可作为弱参考，只用于发现继承流程、历史风险、边界点和命名结构；它仍属于 S4/S3 级参考，不能决定本需求预期。
- 用户没有显式指定相似对象时，不自行寻找旧项目或旧仓库来套用。

#### 非 bug 场景的参考优先级

当需求真源之外还存在多类非规范输入时，默认按以下顺序参考：
1. `PRD`
2. 原型 HTML（如有）
3. PRD 评审会议纪要（如有）
4. 技术评审
5. 技术评审会议纪要（如有）

说明：
- 若某一层输入不存在，则跳过，不强行补位
- 若同层材料之间仍有冲突，必须回到用户澄清或已确认结论，不自行裁决

#### bug 场景的参考说明

- bug 补洞通常不要求建立同样严格的文档优先级
- bug 场景的上下文材料通常更碎、更少、更偏问题导向，按弱参考处理
- bug 场景应优先利用用户对“为什么这是 bug”的说明、复盘记录、修改点说明和必要的白盒辅助信息

### 4.4 授权群聊 Source Discovery

当用户已授权协作文档平台 / IM 读取，且当前输入包可能缺 PRD、技术评审、会议纪要、设计稿或最新澄清时，可以把用户指定的群聊作为低等级 source discovery 入口。

使用边界：
- 群聊记录只用于发现缺失文档链接、会议纪要、设计稿、owner 澄清和需求漂移信号。
- 找到文档链接后，必须读取文档正文并把文档本身纳入 `Source Inventory`；不要只引用“群里有人发过链接”。
- 聊天消息本身不能作为 SSOT，不能直接决定 case 预期；若它与 PRD、评审或设计材料冲突，必须列为 `Open Questions` / `Decision Drift Risk`。
- 如果聊天里只有临时讨论、排期、执行日志、MR、环境问题、截图或短回复，不进入 case 预期，只能作为噪音或执行背景。
- 如果缺失文档在指定群和指定时间窗内仍找不到，再向用户索要，不扩大搜索范围自行猜。

推荐检索顺序：
1. 先按用户给出的本地文档建立输入清单。
2. 检查是否缺 PRD、PRD 评审纪要、技术评审、技术评审纪要、设计稿 / 原型或明确澄清。
3. 只针对缺项或疑似过期项搜索群聊，关键词由任务上下文收敛，例如 `PRD`、`需求`、`评审`、`会议纪要`、`技术评审`、`技术方案`、`设计稿`、`原型`、`结论`、`澄清`、`验收`、`规则`。
4. 按时间线辅助判断：通常先有 PRD，才有 PRD 评审纪要和技术评审；先有技术评审，才有技术评审纪要；设计稿 / 原型可与这条线并行；聊天澄清可能随时出现。
5. 对召回结果只保留候选源清单、可读文档正文、明确冲突和待确认项，不把整段聊天搬进上下文包。

默认消息源由用户当次指定，不预置具体项目 / 群名（仅当用户已授权并指定范围时查找缺失文档）：
- 范围：用户当次给出的文档源 / 消息源清单
- 时间窗：`（脱敏） 00:00:00+08:00` 到 `（脱敏） 23:59:59+08:00`
- 证据等级：群聊消息本身为 `S3`；群聊发现的 PRD / 技术评审 / 设计稿按文档自身类型重新定级。

### 4.5 会议纪要与原声使用规范

- 会议纪要和原声通常来自 AI 转写，可能存在识别错误
- 不得逐字机械采信，必须结合上下文交叉理解
- 默认会议主语言为中文
- PRD、QA、SSOT 等常见英文缩写与中文混用属于正常现象
- 除常见技术术语外，也可能夹杂少量短英文短语，例如 `trade-off`、`kick-off`
- 会议中通常只有一个人开麦
- 因此“转写文本里像是同一个人在持续表达”，不代表观点只来自一个人
- 如果纪要/原声与正式需求口径冲突，应优先回到：
  - 用户澄清
  - PRD 最新口径
  - 已确认的评论或结论

### 4.6 协作文档平台文档与评论优先级规则

- 协作文档平台文档评论不默认是噪音
- 评论里可能包含关键确认、方案调整、范围缩放、规则澄清、例外说明
- 编写 case 时，必须主动检查评论是否包含需求结论

优先级规则：
- 若评论只是讨论，不改变正文语义：以正文为准
- 若评论时间晚于正文最新修改时间，且评论中明确完成以下任一事项：
  - 方案确认
  - 需求修改
  - 范围收敛/扩张
  - 规则澄清
  - 例外说明
  则应以评论口径为准
- 若无法可靠拿到评论时间或正文更新时间：
  - 不自行猜测
  - 必须在写 case 前向用户确认

能力边界说明：
- 如果文档是导出的本地文件，可以读取文件修改时间和导出内容中的评论内容
- 不一定能直接拿到协作文档平台在线文档的真实最新修改时间/评论时间
- 若评论优先级可能影响 case 预期，用户应显式提供“最新正文/评论口径”或相关时间信息

### 4.7 正式写 case 前必须先完成澄清

- 在开始正式写 case 之前，必须先把所有关键不明确点抛给用户
- 只有在没有高影响歧义后，才能进入正式编写

关键不明确点包括但不限于：
- 需求边界
- 多角色职责
- 多端差异
- 异常流是否属于需求范围
- 兼容 / 回退 / 兜底策略
- comment 与正文冲突时的最终口径
- bug 是否已被确认为产品缺陷而不是预期行为

如果还有高影响歧义：
- 只能产出澄清问题或假设清单
- 不得直接生成正式 case

### 4.8 正式写 case 前先交付流程梳理供 review

正式写 case 前，先交付流程梳理供用户 review，以确保理解一致。

这条规则按版本级别和复杂度分层执行：

#### `PATCH`

- 默认不强制流程图

#### `MINOR`

- 如果不影响现有流程，不强制流程图
- 如果影响现有流程：
  - 简单变化：允许用几句话或简化流程描述
  - 复杂变化：必须给局部流程图或流程梳理

#### `MAJOR`

- 强制先给流程图 / 业务流程梳理，再写 case

#### 例外强化条件

即使不是 `MAJOR`，只要满足以下任一项，也应先给流程梳理：
- 涉及多个模块
- 涉及多个端
- 涉及多角色协作
- 涉及状态机 / 阶段切换
- 风险不可控或容易理解偏差

这里的“流程梳理”不限定必须是完整大图，可以是：
- 流程图
- 时序图
- 结构化流程列表
- 仅覆盖受影响部分和其上下游的局部流程图

但正式进入 case 编写前，必须先让用户 review 并确认“流程理解正确”。

### 4.9 双零信任原则

#### 对代码零信任

- 默认实现可能错
- 不因代码现状降低 case 标准
- 不因当前实现已经存在，就把它自动视为正确行为

#### 对需求细节完整性零信任

- 默认 PRD 可能没覆盖：
  - 边界
  - 异常
  - 兼容
  - 用户习惯
  - 功能边界
- 这些缺口必须主动提出来澄清

### 4.10 PRD 显式功能覆盖自校验

PRD、设计稿、原型或评审材料中已经明确、显式标出的内容，默认就是当前 case 资产必须兜住的范围。这里的“明确项”包括：
- 编号小节和小节标题下的功能描述
- 表格中的每一行能力、字段、状态、按钮、文案、限制条件和联动结果
- 原型 / 截图中的可见控件、角标、状态色、错误提示、禁用态、倒计时、列表字段和跳转入口
- 评审或用户澄清中已经钉死的流程、边界、数据口径和不覆盖范围

正式写 case 前必须先生成“显式功能覆盖索引”。每一行至少包含：
- 来源锚点：PRD 章节、页码、表格行、原型位置、截图编号或评审纪要片段
- 需求事实：该明确项要求什么
- 覆盖目标：落到哪个 case、case group、E2E、coverage matrix，或明确标为 `out_of_scope / pending_clarification`
- 覆盖证据：case ID、标题、关键断言、matrix 行或不覆盖说明
- 状态：`covered`、`out_of_scope`、`pending_clarification`、`gap`

模块级覆盖只是一轮粗分解，不是完成定义。完成模块级覆盖后，必须回看 PRD 原文、表格和视觉证据做“细节回填”：
- 如果全部 case 资产中查不到覆盖某个明确项的证据，状态必须是 `gap`
- `gap` 不能进入完成态；必须补 case / matrix，或向用户抛出裁决
- 富文本表格、截图标注、状态色、角标和隐藏在原型交互里的细节，必须作为图示事实进入覆盖索引
- 文本提取没有抽出的表格内容，不能因为不可检索而放过；视觉证据识别出的事实同样要追溯

自校验可以用人工矩阵，也可以配合 `rg` 或脚本反查 case 资产；但最终必须能回答一句话：PRD 中确定要做的每个明确项，在 case 中哪里覆盖了它。

### 4.11 QA 上下文综合

当输入包含多份 PRD、技术评审、会议纪要、OpenSpec、原型、协作文档平台评论、已有 case、bug 或跨模块共享文档时，正式写 case 前必须先形成 QA 上下文包；写完 case 后必须反查该上下文包。

上下文包至少覆盖：
- 源文档清单、归档路径或来源、版本和可定位片段。
- 模块、角色、端、上下游系统和共享资源。
- 已确认规则、待确认问题、冲突和过期材料。
- 数据生产者、存储 / 接口、消费者、回显和落库验证点。
- 阶段、轮次、状态迁移、退出、重连、取消和异常恢复。
- 等价类、边界值、非法值、空值 / 默认值、组合风险和错误推断。
- App、管理后台、公众号 H5、WebView、真机 / 模拟器、微信容器等跨端矩阵。
- 哪些点进入 case，哪些进入 L1 中间层，哪些必须保留到 L2 真机 / 人工体验。

共享文档不能只归到单一模块后沉默使用；必须写明它被哪些业务模块消费，以及这些消费关系如何落到 case 或不覆盖项。

### 4.12 图示与富文本输入门禁

只要输入包含 PDF、docx、PPT、图片、截图、原型、效果图、流程图、时机表、表格、批注、删除线或颜色状态，就不能只靠视觉识别下结论；必须同时保留文本提取和视觉证据。

输入处理至少包含：
- `Source Inventory`：原件路径或来源、版本、页码 / 标题 / 可定位片段。
- `Extracted Text`：可检索文本、表格、批注 / 修订、OCR 或视觉模型提取出的可见文字。
- `Visual Evidence`：关键页或全部页面的渲染图，覆盖表格、流程图、截图标注、颜色状态、删除线、批注和分页附近内容。
- `Manifest`：原件、hash / size、归档时间、来源、文本提取方法、视觉检查方法、提取或识别失败项。

对图示材料，必须补一张轻量映射表：

| 图示位置 | 识别事实 | 风险 / 边界 | 测试点 | case / matrix / 不覆盖项 |
| --- | --- | --- | --- | --- |

如果文本提取和视觉复核冲突，或关键区域不可读 / 截断 / 识别不确定，必须作为高风险缺口进入澄清问题；冲突未澄清时不得进入正式 case 编写。

## 5. 白盒使用边界

### 5.1 新需求 / 新功能 case

- 不看待编写对象自身代码
- 不以待编写对象自身代码决定 case
- 不以待编写对象自身代码反推产品需求
- 用户明确指定的相似旧项目 / 旧仓库 / 旧玩法 / 旧后台，可以弱参考其现有 case、文档或代码，用于发现继承流程、历史风险和边界点
- 相似对象弱参考不能替代当前 PRD、技术评审、设计稿或用户澄清；若冲突，以当前需求真源和已确认口径为准


### 5.2 bug 补洞 / 已实现功能回归

允许看代码，但代码只能帮助：
- 理解 bug 根因
- 补白盒验证点
- 识别边界与异常

禁止：
- 把“当前代码就是这样”当作“预期应该这样”

白盒信息更适合在**测试执行阶段**作为辅助依据，而不是在新需求 case 编写阶段反向决定预期。

## 7. 单条 case 编写规则

### 7.0 方法选择与测试点清单

复杂需求、草案用例矩阵或需要解释覆盖依据时，必须先选择测试设计方法，再展开 case。方法选择参考 `method-selection.md`。

常用映射：
- 有输入范围、长度、格式、上下限：等价类划分 + 边界值分析。
- 有条件组合、开关、身份差异：判定表。
- 有状态变化、生命周期、流程节点：状态迁移。
- 有端到端业务流程：场景法。
- 有大量参数组合且全排列成本过高：正交试验 + 风险补点。

正式展开 case 前，应先列测试点清单或覆盖映射。测试点至少说明：
- 覆盖对象：需求点、风险点或 bug 缺口。
- 主要设计方法：等价类、边界值、判定表、状态迁移、场景法、正交试验或错误推断。
- 计划落点：补验证点、修改旧 case、新增 case、E2E、matrix 或不覆盖项。

每条 P0 / P1 case 必须能解释业务价值，至少追溯到放行风险、核心链路、历史缺口、用户损害或关键业务规则之一。

### 7.1 标题

- 标题必须是低理解成本、用户可观察结果导向
- 不使用纯内部状态机术语做标题，除非该术语本身就是产品术语

### 7.2 操作步骤

- 步骤按编号逐条写
- 每一步都应由执行人直接照做，不依赖作者口头补充
- 多人场景要写明：谁操作、谁观察、在哪些端观察

### 7.3 预期结果

- 与步骤一一对应
- 每条只保留最核心的页面结果与技术检查点
- 每条 case 应写明具体测试数据和主要设计方法；若不适用，应说明不适用原因
- 技术检查点应尽量写成明确值，而不是“相比上一步 +1”这类需要换算的描述
- 预期必须可追溯到 `S1 / S2` 输入
- 对存在明确前后态的功能，预期默认至少覆盖：操作前状态、操作后状态、重复操作是否被阻断或去重
- 对计数、额度、预约人数、聚合展示等数据联动项，默认验证“前端展示值与后端最新返回/落库一致”，而不是默认假设前端会自行重算
- 对依赖“来源/类型/原因”区分的业务，技术检查点不能只验数值变化，还应验证该次变化可被明确归因为对应来源，例如初始发放、后台调整、游戏消耗

### 7.3.0 业务边界定义门禁

任何由时间、阶段、状态、范围、角色、对象归属或集合边界决定“是否生效”的功能，都必须先写业务定义层面的边界，再写实现证据。

至少检查：

- 业务边界：PRD、原型或用户确认口径中定义的生效范围、起止条件、归属对象和不生效范围。
- 实现映射：OpenSpec、状态机事件、IDL、接口、日志或存储只能说明系统如何识别边界，不能替代业务边界本身。
- 正向存在：该生效时必须生效、该展示时必须展示、该计入时必须计入、该可操作时必须可操作；不能只写“有数据”或“按钮可点”，要写清具体对象、范围和来源。
- 反向不存在：不该生效时必须不生效、不该展示时必须不展示、不该计入时必须不计入、不该可操作时必须不可操作；不能只写正向路径。
- 隔离性：跨对象、跨角色、跨状态、跨轮次、跨列表、跨页面、跨会话或换绑后的旧对象不能继续消费新结果；如果数据可从其他作用域查询到，case 必须显式断言那里没有它。
- 切换与残留：边界切换前后、重复触发、取消、失败、恢复、刷新、重进或重连后，旧状态、旧结果、旧权限和旧对象不得残留到新作用域。
- 事实与结果：若系统同时保留原始事实和业务结果，必须区分“原始事实留档”和“业务结果生效”。

正反边界的最低断言集：

1. A 条件下，目标结果必须出现。
2. 非 A 条件下，目标结果不得出现。
3. A 条件产生的结果不得出现在 B/C/其他作用域中。
4. 从 A 切到 B 后，A 的结果不得残留影响 B；B 失败时不得覆盖最后一个有效状态。

例子只作映射参考：

- 普通后台：分页/筛选集合、权限可见范围、状态筛选、导出时间范围、配置生效范围、换绑后当前对象归属。
- 多端产品：房主与非房主、发布端与消费端、A 端操作 B 端观察、旧端缓存与新端刷新。
- 实时互动：弹幕、礼物、点击、投票等独立数据通道应分别验证窗口内生效、窗口外不生效、原始留档和跨轮/跨会话不串。

### 7.3.1 变更后一致性门禁

凡 case 涉及新增、编辑、删除、上下架、状态流转、补填信息、配额调整、计数变化、预约人数变化或任何会改变服务端状态的操作，默认必须覆盖以下检查点；除非明确不适用，否则不能只写“保存成功”：

1. 操作前状态：页面、接口或可查询数据中的原始值。
2. 提交值：本次表单、按钮、参数或动作实际提交的值。
3. 接口请求与响应：关键字段、状态码、错误码和业务响应值与提交意图一致。
4. 持久化或可查询值：数据库、详情接口、列表接口或服务端查询结果与提交值一致。
5. 刷新回显：刷新页面、重新进入详情或重新打开弹窗后仍展示最新值。
6. 下游消费：若该字段会被客户端、H5、运营后台其他页面、媒体网关或统计口径消费，消费端读到的值也必须一致。
7. 重复/反向操作：重复提交、撤销、上下架反向动作、重复预约等应被去重或按需求收敛。

### 7.3.2 黑盒数据设计门禁

对存在长度、数量、金额、时间、枚举、比例、文件大小、人数、轮次、次数等约束的字段，必须给具体测试数据，不允许只写“输入合法/非法值”。默认使用传统黑盒方法组合：

- 等价类：有效类、无效类、空值/默认值、格式错误类、权限错误类。
- 边界值：`min`、`min+1`、典型值、`max-1`、`max`、`max+1`；若允许空，再单列空值。
- 状态转移：每个合法状态、非法状态跳转、重复跳转、回退/恢复、终态后继续操作。
- 错误推断：前导零、空格、超长中文/英文/emoji、特殊字符、重复点击、网络重试、历史残留、缓存命中、权限错配。

例：字段“主播名称允许空，最多 50 字”时，至少覆盖空、1 字、49 字、50 字、51 字；如果前端输入框限制无法输入 51 字，也要记录“前端阻止输入 51 字”这一行为，并补接口或后端越界拒绝检查。若该字段会在公众号展示，还必须追加消费端长文案展示检查。

如果行为随业务类型、状态、平台、入口、时间窗口、链接/媒体是否存在、是否上架、是否补填等维度变化，必须先写变体矩阵，不能用一个样本代表全部。每个被选中的矩阵行都要有自己的测试数据、提交/回显或可查询值、消费端预期；不纳入的矩阵行必须标为 `out_of_scope`、`pending_clarification` 或 `gap` 并说明原因。

### 7.3.3 多轮/状态机重置门禁

对多轮游戏、多阶段流程、审批流、节目状态流、任务状态流等状态机，必须按“进入、停留、退出、下一阶段、下一轮、终局”拆验证点。至少检查：

- 阶段进入：只出现当前阶段允许的按钮、文案、图层、音频、字幕、倒计时和数据。
- 阶段停留：等待、超时、长时间未操作、部分角色已提交时不会错误推进或泄露调试/旧文案。
- 阶段退出：弹窗、loading、toast、OS、字幕、音频、视频流、图层、临时输入和缓存清理。
- 下一阶段：上一阶段结果只在允许范围内被使用，不串场、不残留。
- 下一轮：上一轮输入、选择、命中、分数、徽章、图片、参考图、Ready 状态和倒计时按需求重置。
- 终局：终态后不再出现前序阶段 CTA，不进入下一轮，不继续触发阶段音频/字幕/状态机事件。

如果新需求基于旧版本、旧玩法或公共流程改造，必须先列出：
- 继承旧流程的步骤、OS、状态、UI 元素。
- 本 PRD 覆盖旧流程的步骤、OS、状态、UI 元素。
- 不确定是否继承的差异点。

PRD 中的专属 OS 表、阶段图、效果图、时机图和示例截图都要参与断言设计；不能因为开发复用了旧模块，就把旧模块行为当成新需求的默认预期。

如果用户只是说“类似某旧项目 / 旧仓库”，还必须把相似对象降级为参考材料：
- 可借用：模块拆分、流程骨架、历史缺陷类型、边界样本、命名或数据准备方式
- 不可借用：预期结果、验收口径、优先级结论、当前需求未确认的异常流
- 若相似对象材料和当前 S1/S2 冲突，按当前 S1/S2 写 case，并把冲突列为待确认或不沿用说明

### 7.3.4 跨端/跨模块消费门禁

凡一个对象、模块、服务或端生产配置、状态、链接、媒体、人数、配额、图片或文本，另一个对象、模块、服务或端消费它，必须写交叉验证。下面只是常见例子，不是适用范围上限：

- 配置生产端 -> H5/客户端/后台其他页面展示。
- 内容补填/上下架 -> 公开页面、列表、详情、回放或分享入口。
- 服务端状态 -> 列表、详情、客户端阶段或通知。
- 图片/视频生成或上传 -> 媒体网关鉴权、预览、下载、保存。
- 前端展示时机 -> 宿主容器、native bridge、RTC、AI/媒体消费端。

交叉验证必须写清：生产端设置了什么、消费端在哪里观察、消费端预期展示/隐藏/跳转/播放什么、刷新或重新进入后是否仍一致。

跨端链路如果存在集合关系，不能只验证消费端“包含某一条新数据”。必须定义生产端 eligible set、消费端过滤口径、稳定 join key、排序/分页范围和缺失/多余对象处理；若产品口径是全量一致，则要断言两端集合相等。

### 7.3.5 视觉压力样本门禁

视觉类 case 不允许只写“不遮挡、不拉伸、不超出”。必须至少给出 1-3 个压力样本：

- 文本：空、1 字、边界长度、超长中文、英文长单词、数字、emoji。
- 数值：0、前导零、最大值、越界值。
- 图片/视频：方图、竖图、横图、低清图、大文件、空链接、无权限链接。
- 状态叠加：徽章、标签、昵称、Ready、倒计时、按钮、弹窗、字幕、OS、音频同时出现。
- 端差异：iPhone 小屏/大屏、微信 H5、桌面浏览器、iOS WebView、管理后台宽屏/窄屏。

如果字段会跨端展示，视觉压力样本必须覆盖消费端，例如后台主播名称超长时，公众号节目卡也要验证换行、截断、省略和不遮挡。

### 7.3.6 异步残留门禁

涉及音频、字幕、OS、视频流、WebSocket、RTC、WebView bridge、动画、loading、toast、弹窗、轮询、缓存或重连时，必须检查“触发、取消、完成、切阶段、重进页面、刷新/重连”后的残留：

- 不继续播放上一阶段音频或警报。
- 不显示上一阶段字幕、toast、loading 或程序文案。
- 不保留旧视频流、旧图片、旧参考图或旧图层。
- 不重复触发拍照、提交、倒计时、超时或状态流转事件。
- 重进页面后状态与服务端最新状态一致。

### 7.3.7 交互命中与手势门禁

涉及链接、按钮、列表项、热区、滑杆、拖拽贴纸、边缘区域或长按/滑动/拖拽手势时，case 不能只验证“点击后可用”，还必须确认交互命中范围与平台手势不会造成误触：

- 命中范围：只有设计或常识上应可交互的文案、图标、按钮或控件区域触发动作；容器空白、说明文字、分隔线、整行背景等非目标区域不触发。
- 反向样本：点击/拖拽目标区域外侧、相邻控件、卡片边缘、屏幕边缘时，不应跳转、提交、取消、误调数值或触发系统返回手势。
- 状态样本：禁用、loading、处理中、已取消、已过期、无权限、非房主等状态下，命中目标也不能绕过状态限制。
- 端差异：iPhone 小屏、刘海/灵动岛、安全区、微信 H5、iOS WebView 和桌面浏览器至少按风险选择覆盖，尤其是滑杆、贴纸拖拽和靠近屏幕边缘的控件。
- 嵌套手势：当页面同时存在页面级横滑/纵滑、列表滚动、图片轮播、卡片横滑或拖拽时，必须验证当前焦点归属、滑动方向识别、内层操作不会误触外层切页，外层切页也不会吞掉内层预期操作。

### 7.3.8 数据来源、环境开关与冷启动门禁

涉及服务端下发值、运营配置、日期相关展示、配额、预约人数、mock 数据、feature flag、联调开关、缓存或首屏默认值时，必须把“数据从哪里来”和“当前环境是否启用该能力”写成前置与断言：

- 环境前置：明确开关、灰度、泳道、测试配置、mock 状态和依赖服务是否启用；若开关关闭或环境不满足，应标记为 BLOCKED/环境问题，而不是直接判定产品失败。
- 数据来源：用可区分的服务端值、日期值或后台配置值验证页面不是硬编码、静态 mock、默认占位或旧缓存，例如不要只用默认配额 `3` 或固定“今日节目”样本。
- 冷启动与重进：首次安装、首次进入页面、杀进程重启、返回首页、刷新 H5、日期跨天、后台修改后重进，都要按风险验证最新服务端值替换占位值。
- 缓存收敛：允许缓存时要写清刷新时机、失效条件和最终一致性；不允许缓存时，重新进入必须直接读到最新值。

### 7.3.9 多人对象绑定门禁

多人、多角色或多媒体链路中，只验证“页面有变化”不够；必须检查变化是否绑定到正确的人、座次、角色和资源：

- 身份绑定：用户 ID、昵称、座次、房主/玩家角色、Ready 状态、踢人/退出/重连后的成员关系一致。
- 权限绑定：房主权限转移、非房主禁用项、全员 Ready 门禁、切游戏后重新准备门禁都要同时在操作者与观察者端验证。
- 资源绑定：视频流、AI/媒体流、图片、音频、聊天/静音策略、配额扣减和结算结果必须消费当前对象的数据，不能串到旧座次、旧角色或其他对象。
- 请求生命周期：发起、取消、拒绝、接受、超时、重复响应、切阶段、离房/重连后，旧请求不能继续生效或被后来接受。

### 7.3.10 公开 H5 / 公众号兼容性矩阵门禁

公开 H5、WebView、App 页面、公众号页面、桌面 Web 等面向全量用户发布的页面，兼容性 case 不能只写“iPhone/Android 兼容”。必须给出可执行矩阵：

- 容器：微信移动端 WebView、微信 iPad/平板、桌面微信、必要时补浏览器打开的降级行为。
- 系统：目标容器官方最低支持系统、当前主流系统、当前最新系统至少各一类。
- 设备：小屏、大屏、刘海/安全区、平板、折叠屏/横竖屏、低性能旧机、主流品牌 Android、HarmonyOS。
- 版本：执行时记录微信版本、系统版本、设备型号和字体/显示缩放；若官方最低要求变化，应更新最低系统行。
- 链路：首屏、Tab、滚动/滑动、核心按钮、弹窗、图片/视频资产、返回、刷新/重进、弱网恢复。
- 展示压力：字体放大、显示缩放、长文案、图片比例、键盘/弹窗、安全区和桌面窗口缩放。

面向全量用户发布的页面，至少应有一条 P0 发布门禁 case，输出矩阵执行表和失败设备证据；不能只依赖单台 iPhone 或单台 Android 作为兼容性结论。

### 7.3.11 集合语义与跨视图一致性门禁

当页面区域、接口参数或产品文案表达集合语义时，case 必须验证“集合里应该有什么、不应该有什么、边界对象如何处理”，不能只验证列表有数据。典型语义包括“今日、全部、我的、即将、已结束、待发布、已发布、推荐、最近、热门、可见、已上架”。

至少检查：

- 同一对象出现在多个列表、Tab、弹层、卡片、条带或详情页时，状态、数量、按钮态、文案、媒体、排序和刷新后收敛一致。
- 聚合条带、计数、最近时间、总人数、汇总金额等展示值，与明细列表和服务端查询口径一致；若产品允许口径不同，必须写明差异来源。
- 集合文案与数据筛选一致，例如“即将”不应混入已结束对象，“今日”不应混入非当天对象，“我的”不应混入其他身份对象。
- 后台修改、上下架、状态流转、预约/取消/补填/发布后，所有消费视图重新进入或刷新后都收敛到同一业务事实。

### 7.3.12 空值、默认值与待后补字段消费门禁

PRD 允许某字段为空、默认、待后补、后续上传或由运营稍后填写时，不能只验证生产端可保存；必须验证所有消费端的过滤、兜底、占位、隐藏或错误提示。

至少检查：

- 时间、链接、图片、视频、标题、封面、状态、数量、权重、排序值为空或默认时，消费端不会展示系统哨兵值、错误日期、断链、空白页或误导性 CTA。
- 允许为空的字段如果参与排序、分组、筛选、聚合、最近时间或状态推导，必须明确空值对象是否纳入集合，以及纳入后的排序和展示规则。
- 待后补字段补齐后，列表、详情、H5/客户端、统计或分享等消费端刷新后能从占位态收敛到真实值。

### 7.3.13 性能预算与数据规模门禁

面向真实用户的 H5、WebView、公开 Web、管理后台核心列表和首屏链路，必须按数据规模设计性能 case。即使 PRD 没写具体秒数，也要用技术评审、接口设计、行业常识、用户体感或用户确认口径提出预算或风险提示。

至少检查：

- 首屏关键内容的可见时间预算、白屏时间预算、核心接口结束时间、总请求数、并发请求数、图片/视频体积、关键资源缓存和弱网表现。
- 列表、Tab、纪念品、评论、资产、详情等非首屏数据不应阻塞首屏；若必须阻塞，技术评审应说明原因和上限。
- 识别 N+1、全量分页、逐条 detail、重复 preflight、超大原图、未缩略图、未懒加载、签名/授权阻塞首屏等结构性风险。
- 性能 case 的证据口径应包含 HAR、Performance 截图、接口耗时统计或等效日志，并注明测试数据量、设备/容器、网络条件和版本。

### 7.3.14 结构性模型升级门禁

当需求从单对象升级为多分类、多对象、可排序、可替换、可删除、可折叠、可分页或跨区域消费时，必须先判断旧 case 模型是否整体过期，不能只在旧 case 后面补一条新增能力。

至少检查：

- 旧的单记录、单视频、单链接、单状态、单列表 case 是否仍成立；不成立时重写整组 case。
- 新模型的分类集合、每类数量、排序、增删改查、替换、软删除、重排、权限、空态和下游消费都要有覆盖。
- 多分类媒体或 Tab 不能用一个素材代表全部分类。每个被选分类都要有可区分的标题、文件或业务键，并在生产端回显、聚合接口和消费端展示中逐类断言；只看到总数增加、任意一条视频可见，或只覆盖默认 Tab，都不能证明分类隔离和下游消费正确。
- 如果新模型会同时影响管理后台、H5、客户端、接口和数据表，必须把生产端、聚合接口、消费端展示和刷新回显串成端到端 case 或覆盖矩阵。

### 7.4 视角

- 操作步骤坚持黑盒用户视角
- 预期结果允许融合页面、接口、状态、存储等核心检查点
- 不替第三方服务本身背锅，只验证我们自己的入口、契约、兜底和收束
- 涉及第三方平台、外部容器或系统限制时，必须先确认产品真实承诺的是“直接跳转”“展示链接”“复制链接”还是其他替代方案，不能默认按最理想形态写 case
- 同名能力如果在不同业务对象上的状态机、入口、结果或约束不同，应拆成独立 case，而不是混写成“一个功能全覆盖”；例如直播预约与录播预约、平台跳转与链接复制
- 如果某个交互只能在真实容器/真机中观察，例如微信真机外跳、系统分享、权限弹窗或宿主 bridge，case 应把“自动化可观察的数据/UI一致性”和“真机人工目标证明”拆成两个检查点，不允许用源码存在性替代用户视角证据。

### 7.5 可读性约束

case 必须对以下人群都可读：
- PM
- 开发
- QA
- 使用 agent 的协作者

因此 case 应满足：
- 标题是结果导向，而不是内部状态导向
- 步骤与预期一一对应
- 避免只有作者自己懂的简称
- 如果使用缩写，默认采用团队常用缩写
- 多角色、多端、多阶段必须明确标出观察主体
- 技术验证点尽量写成明确值或明确判断方式

### 7.6 常识性 bad case / 通用品质要求

- case 不只覆盖 PRD 上写明的显性功能点
- 还必须覆盖会直接影响用户体验、且正常测试中一定不能接受的常识性 bad case

例如：
- 多人连麦回音
- 语音延迟超过可接受阈值
- 明显卡死
- 无法恢复
- 多端同步严重错位
- 核心交互出现明显不可接受体验

这些不是“额外发挥”，而是产品常识与平台常识下的基础负向验收项。

### 7.7 范围裁剪规则

- PRD 中标记为：
  - `待定`
  - `废弃`
  - `暂不实现`
  - `后续再议`
  的内容，不强制纳入当前 case
- 当 PRD 更新后，再重新生成或补写
- 如果这些内容虽在正文中标记待定，但又在评论/澄清中被重新激活，应按最新有效口径处理

### 7.8 假设与不覆盖项

- 如果带假设写作，必须单独列出假设，不能混进正式预期
- 对当前明确不覆盖的范围，要显式写出来，避免被误解为遗漏
- 对 bug 驱动的增补，应明确：
  - 原 case 为什么没挡住
  - 这次补的是验证点、边界还是新 case

### 7.9 覆盖追踪关系

- 每个 case 或 case 组，必须能明确追溯其覆盖的是哪类需求点、风险点或 bug 缺口；如果输入有 PRD 编号章节、表格或原型可见控件，还必须能反查到对应来源锚点
- 当同一批 case 同时覆盖多个对象时，应显式说明主覆盖对象与附带覆盖对象
- 不要求所有产品都立刻引入复杂矩阵，但必须让读者看得出“这条 case 为什么存在”，以及 PRD 中确定要做的内容是否还有 `gap`

## 8. E2E 编写规则

- E2E 不是“单条 case 列表”，而是“覆盖链路”
- 每条 E2E 都必须有：
  - 前提条件
  - 操作步骤
  - 预期结果
  - 关联单条用例
  - 端到端成功标准

- E2E 应区分：
  - 后端先验证的链路
  - 客户端补体验与真实交互的链路

- 每条关键主流程至少检查以下异常流是否需要纳入：
  - 输入异常
  - 状态切换异常
  - 权限 / 角色异常
  - 网络 / 重试 / 恢复异常

- E2E 若覆盖的对象存在类型、状态或字段变体，必须说明本条 E2E 覆盖哪些矩阵行，以及哪些行由其他 E2E、全量回归、L1 自动化或人工边界覆盖。不能因为一条主流程跑通，就声称同一功能所有类型/状态都通过。
- E2E 的通过条件必须来自用户链路证据：UI、真实请求/响应、读回、跨端消费、日志/timeline 或人工真机证据。源码检查可以帮助定位，但不能成为 E2E 成功标准。

## 9. 优先级与执行分层

建议统一保留 4 层心智：

1. `Launch Gate`
说明：最小放行集，解决“能不能继续发”

2. `P0 / Smoke`
说明：版本底线集，解决“哪些问题失败即不可接受”

3. `Main Regression`
说明：P0 + 关键 P1，解决“主回归必须覆盖什么”

4. `Full Regression`
说明：全量 case，解决“完整留档与全风险回归”

注意：
- `Launch Gate` 不等于 `P0`
- 不要为了缩小执行集而错误降低 `P0`

### 9.1 产品 L1 与真机边界

产品相关 case 若涉及自动化、E2E 或 CI/CD，应额外标注候选边界，供 下游环节 后续拆解；层级与术语定义由本规范对应节给出：
- 候选稳定机器断言：接口、DB、日志、timeline、页面元素、客户端事件、状态机主动推进、跨轮重置、对象绑定、回显 / 落库 / 下游消费一致性。
- 必须保留到 L2 的真机 / 人工项：主设备真机性能、发热、真实网络、RTC / S2S、多人隔离音频、视觉参考质量、人像 / 法像、模糊、S2S 内容识别准确率和用户可接受等待。
- 模拟器通过的边界：不覆盖真机发热、网络、权限细节、音频回声、真机视觉观感，也不替代完整一局准入。

若某条 case 需要进入 CI/CD，本规范只要求在 case 层标出候选检查点；开发侧 SSOT、L1 manifest、runner map 和 routing gap 由 下游环节 负责生成。若只能由真机或人工判断，应明确标为 `manual-real-device`、`manual-visual`、`manual-audio-oracle` 或真机准入项。

## 10. 版本规则

统一采用三级版本号：

`vMAJOR.MINOR.PATCH`

- `MAJOR`
  - 对应 PRD 大需求 / 产品立项 / 强制升级代际 / 不兼容的大版本

- `MINOR`
  - 对应 PRD 小变更 / 阶段版本 / 同代际下的功能阶段

- `PATCH`
  - 对应与 PRD 无关的 case 修订、编排优化、补充异常、完善结构

### 10.1 使用规则

- 套件版本必须写进：
  - `test-cases.md`
  - `e2e-cases.md`
  - `test-cases.yaml`
  - `e2e-cases.yaml`
  - `mr-ready-note.md`

- 同一次提交中，涉及 case 真源结构性调整时必须同步更新版本号
- 当版本号发生需求变更级别的升级时，至少指 `MAJOR` 或 `MINOR` 递增，除 case 本身外，还必须同步生成或更新：
  - `review-atlas.docx`
  - `review-atlas-assets/` 下的对应评审图示文件，如 `SVG/PNG`
  - `mr-ready-note.md` 中的版本说明与评审说明

## 11. 编写完成定义

只有同时满足以下条件，才可视为本次 case 编写完成：

- 已明确本次任务类型与影响范围
- 已完成输入与前置检查
- 已完成必要的澄清
- 如适用，已完成流程梳理并经用户确认
- 已修改 `Markdown` 真源
- 若涉及结构性变更，已同步对应 `YAML`
- 已检查是否需要联动更新：
  - `e2e-cases`
  - `coverage-matrix`
  - `mr-ready-note`
  - 版本号
- 若输入包含关键图示 / 富文本材料，已完成文本提取、视觉证据、manifest、图示事实映射和冲突处理
- 所有新增/改写 case 的预期都可追溯到需求真源或已确认澄清
- 已用 QA 上下文包反查 case 是否覆盖流程、数据流、状态模型、边界矩阵、跨端消费和不覆盖项
- 已调用 `生成后自检门禁` 完成生成后自检门禁；若存在活跃 finding，已向用户抛出标题、严重级别、影响和 fix 方向，并记录用户裁决或待裁决状态
- 已在 case 层标注候选 L1 可机器断言点、L2 真机 / 人工体验点，以及模拟器通过无法覆盖的风险
- 若产出 `review-atlas` 或其他评审图，已生成嵌入正式 PNG 的 `review-atlas.docx`，保留可编辑 `SVG`、正式导出 `PNG`，并完成视觉验收


完成判据的真源是 `SKILL.md`「完成判据」节；正式资产用 `check_assets.py --dir <资产目录>`，轻量模式用 `--dir <资产目录> --light`，按 `EVIDENCE_JSON.observations` 由独立执行方复算，`ok` / 退出码只作辅助。
如果输入不够，不能伪装成“已完成”，必须明确标记为：
- 待补输入后继续

## 12. 对下游断言路由的衔接

后续若要让开发 E2E、TDD/BDD、QA L1 或 agent runner 直接消费 case，应切到 下游环节，由它基于 case SSOT 生成 assertion manifest、开发侧断言、L1 断言和 routing gap。本 skill 不负责评审 case、改造 case 供下游消费、生成 runner manifest 或编写自动化脚本。

case 资产中可以保留候选字段或说明：
- `execution_target`
- `setup_strategy`
- `oracle_type`
- `evidence_required`
- `controllability_class`
- `role_model`

这些字段不是当前所有产品立刻强制要求，也不是本 skill 的最终执行协议；它们只是给下游断言路由保留的输入线索。

## 13. 自检门禁的触发与处理

### 13.1 触发时机

每生成一版正式 case 资产后，必须立即调用 `生成后自检门禁` 做一次 生成后自检。这里的“一版”包括：
- 从 0 新建 case 套件
- 大范围改写现有 case
- 新增或重排 E2E / coverage matrix
- 对用户裁决后的 case 进行二次收敛

轻量测试点分析或草案矩阵不强制触发；一旦落正式 case 文件，就必须触发。

### 13.2 处理规则

- 如果 `生成后自检门禁` 没有活跃 finding，记录“生成后自检门禁 无需关注项”，可以继续后续流程。
- 如果有活跃 finding，必须向用户汇总每条 finding 的标题、严重级别、影响、fix 方向和需要裁决的问题。
- 用户给出裁决后，按裁决修改 case 资产，并重新跑结构校验。
- 对已经修复的 finding，必须在 `生成后自检门禁` 中记录 accepted / patched / pending 状态，避免下一轮把旧问题当成新问题。
- 若仍有 pending finding，必须在最终答复中明确它是待决策、待外部输入，还是已接受但暂不修改。

### 13.3 生成后自检门禁 常见反馈要前置收口

以下问题不应等到 生成后自检门禁 才发现，写 case 时就要主动避免：

- 正反向边界不精细：模式分流、入口分支、状态分支、权限分支、合法/非法输入、范围归属、窗口计数、集合筛选都必须同时写清“该有时有、该没有时没有、其他作用域没有、切换后不残留”。只断言正向存在，或只写“不可进入/不可操作”但没有验证其他列表/轮次/角色/会话不出现，视为未完成。
- 跨资产引用不一致：`case.e2e_refs`、`e2e-cases.cases`、`coverage-matrix`、`mr-ready-note` 必须双向一致，不能只保证 ID 存在。
- 聚合断言不可复算：累计值、金额、计数、榜单、导出对账必须写清统计范围、时间窗、去重键、单位、标准化口径、异常事件处理和可复算来源。若 schema 或口径未确认，写成待确认项或探索性记录项，不写成强断言。
- 文案歧义：同一规则在概览 case 与边界 case 中不能出现相互冲突的表达；概览只写入口差异，细边界放到专门 case。

## 生成后自检门禁

正式生成一版 case 资产后执行本门禁。

- **执行者**：产出方发起，由独立复核方按下列检查项复算；产出方不宣布放行。
- **检查项**：① 显式覆盖索引 `gap` = 0；② case ID 在真源与派生产物双向一致；③ 主/诊断断言分层；④ 边界成对与切换后残留；⑤ 假设项与不覆盖项已写。
- **输出**：逐项原始观测量 + 活跃 finding 清单（标题 / 严重度 / 影响 / 修复方向）。
- **活跃 finding 定义**：任一检查项未通过或证据不可复算。有则逐条抛给用户裁决，裁决后重跑结构校验并再次执行本门禁；无则记录「无需关注项」可继续。
