# 源文档留存与交叉验证

源文档（PRD、需求 / 设计文档、会议纪要、截图、PDF、docx、导出件）
是**需求真源之一**，不能只依赖会话短期上下文或代码反推预期。

## 归档

- 用户上传源文档后默认**本地留档**（除非明确要求不保存）
- 留档位置在**工作区外的归档目录**，不放业务 repo、Downloads 或临时目录
- 归档保留：原始文件、提取文本、视觉证据、`manifest.json`
- 敏感信息仍按本地私有留档处理；用户要求一次性使用时，跳过归档并在结论中
  标记"上下文不可长期复用"

```
<archive-root>/<project-or-topic>/<YYYYMMDD-HHMMSS>-<short-slug>/
  originals/   extracted/   visual/   manifest.json   notes.md
```

`manifest.json` 至少记录：原始文件名与归档路径、sha256、文件大小、归档时间、
来源说明 / 任务名、**文本提取方法**、**视觉检查方法**、**提取或识别失败项**。

## 富文本必须走两道工序

1. **文字提取**：PDF 用成熟提取工具；docx 要读正文、标题、表格、**批注与修订**；
   图片 / 扫描件用 OCR 或视觉模型
2. **视觉校验**：PDF / docx / PPT / 图片 / 截图类材料，保留关键页渲染图，
   对标题、表格、流程图、截图标注、颜色状态、删除线 / 批注、分页附近内容做复核

> **文本提取与视觉内容不一致时，以视觉复核发现的问题为高风险缺口，不能静默忽略。**

> 需要 OCR 时用 `screenshot-ocr`：先判断是不是电子文本渲染（能拿到原始文本就是构造性 100%），
> 低容错文档一律 server 级模型 + 双引擎分歧定位 + 盲读语义校对。

## 任务结束前交叉验证

输出 case、测试结论、bug 判断或方案前，回看归档源文档：

- 是否覆盖主流程、边界、异常、角色差异
- 是否存在**根据代码或经验自行补出来的预期**
- 是否遗漏表格、截图、流程图、批注、删除线或会议纪要中的约束
- 源文档缺失 / 提取失败 / 识别不确定 → **在结论中写明缺口**
- **最终输出应引用归档路径、文档名、页码 / 章节 / 标题或可定位片段**
